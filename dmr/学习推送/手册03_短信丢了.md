# DMR 实战手册 03：短信发送成功，为什么对方没有收到？

> 第二阶段 · DMR 嵌入式协议排障 · 基础理解篇
>
> 接在《手册01_登记失败三问》《手册02_Grant了没声》之后。本篇不再新增正式课程序号，课程第40课已经收官。
>
> 阅读目标：分清本机发送、空口链路确认、接收端重组、应用显示四层；能通过数据头、确认响应和接收日志定位短信失败原因。示意频率/ID/日志均为教学样例，不代表真实抓包。

## 1. 一个现场故事：发送方明明显示“成功”

用户A发送“请到东门集合”，A屏幕显示“发送成功”；B收件箱却没有新消息。

不要立即断言“短信在空口丢了”。首先问：A所谓的“成功”指的是哪一层？

| 层面 | 可能的设备实现 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| 本机提交 | UI把文字交给消息队列 | 本地受理 | RF已发送、对端已收 |
| 射频发送 | 已提交/发出Data Header和若干Data Blocks | 本机走过TX流程 | B已完整收到 |
| DMR链路确认 | 收到与本次事务匹配的DLL确认 | 协议相应的数据传递完成 | 用户看过短信 |
| 应用送达回执 | B应用显式回报已处理消息 | 应用层达到了所定义的送达状态 | 人已阅读 |
| 已读回执 | 应用显式上报阅读事件 | 客户端报告“已读” | 一定由本人认真阅读 |

**链路层ACK绝不自动等于“用户已读”。** 厂商UI上的“发送成功”是否意味着某个回执，必须结合产品定义和实测日志确认。

## 2. 完整链路图：不要只盯一个RF包

```text
发送端                               接收端
用户文本
  ↓ UTF编码/厂商应用封装
应用消息                              应用收件箱/UI
  ↓                                      ↑
选择承载方案                        字符解码/存储/通知
  ↓                                      ↑
Data Header + Blocks                 完整消息重组
  ↓                                      ↑
FEC/交织/CRC                        完整性和顺序检查
  ↓                                      ↑
RF/Tier II接入或Tier III数据资源 ─→ RX Data Header/Blocks
  ↑                                      │
  └──────── 可选的DLL响应 ──────────────┘
```

发送端链路确认与接收端UI是否显示，是两段不同的链路。Tier III还可能存在控制信道请求、数据业务资源分配、返回控制信道等过程；Tier II则有其信道接入条件。不要把语音Grant流程原封不动套在所有数据业务上。

## 3. 最容易混的三类数据业务

### 3.1 IP承载的Text Messaging

ETSI TS 102 361-3 V1.3.1 §5.7.1定义IP承载下的Text Messaging，规定字符编码为BMP范围的UTF-16BE，建议默认无线网络UDP端口5016，且端口宜可配置。这**只是在这种标准IP消息路径下**的要求，不能推广为“所有DMR短信都固定用端口5016”。

```text
消息文本
  ↓ UTF-16BE (标准IP文本业务)
UDP datagram
  ↓ 可选的UDP/IPv4压缩
DMR PDP / DLL
  ↓
空口数据突发
```

如果抓到了完整UDP/IP应用数据，但设备不显示短信，优先检查字符编码、端口、应用协议、联系人/过滤与存储，而不是继续提高射频功率。

### 3.2 Short Data承载

§6还规定Short Data Bearer Service，包括Defined Data、Raw Data、Status/Precoded等格式。Short Data可以是Confirmed或Unconfirmed，并不要求“一条短消息只有一个Burst”。

```text
Data Header
   ↓
Data Block 1
   ↓
Data Block 2
   ↓
...
   ↓
Last Data Block (Message CRC32)
```

不同Short Data子类型的字段、是否携带Appended Blocks、确认机制不完全一样。尤其Status/Precoded可以只由Header承载，不能把它误当作一定要有数据块的自由文本短信。

### 3.3 厂商扩展

Motorola、Hytera或其他设备可能使用特定应用协议、厂商私有头、端口及文本格式；具体互通能力取决于双方支持哪些服务。不能只因为两台机器都是DMR、RF同步正确，就断言文本一定能互通。

**排障第一刀：先确认业务承载模式，再按相应格式解包。**

## 4. Confirmed / Unconfirmed：用户界面不能乱翻译

根据TS 102 361-3 V1.3.1 §6.4 Table 6.5，Short Data的 `A` 与 `SARQ` 组合为：

| A | SARQ | 标准语义 |
|---|---|---|
| 0 | 0 | Unconfirmed，不要求响应 |
| 0 | 1 | 保留 |
| 1 | 0 | Confirmed，对整条消息进行确认 |
| 1 | 1 | Confirmed，支持按块选择性重传 |

规范还指出Short Data响应只支持Stop-and-Wait流控，不能因为在普通PDP中看见Sliding Window，就直接认为短数据也使用相同机制。

对应的Short Data Response包括：
- ACK：所有相关数据块成功接收。
- NACK：例如非法格式、整包CRC失败、接收端存储空间不足、不可递送。
- SACK：指出需要选择性重发的块。

这些名称属于**数据包响应**，和第34课Tier III控制信令中的C_ACKD/C_NACKD/Reason不是同一组PDU，日志、枚举和状态机必须分开。

```text
Tier III Control Plane:
C_ACKD / C_NACKD / Reason

DMR Data Packet Response:
C_RHEAD → Class / Type / Status
（必要时 C_RDATA 指出选择性重发块）
```

### 为什么“确认模式”也会失败？

接收机可能已经收到数据头和部分Block，但最后一个Block被干扰，Message CRC32不通过，或者确认响应本身丢失。

```text
A: DATA HEADER ────────────→ B: Header OK
A: BLOCK 1 ───────────────→ B: Block1 OK
A: BLOCK 2 ─── 被干扰 ──X B: Missing / CRC fail
A: LAST BLOCK ───────────→ B: 有末块，但整包不完整
A: 等响应                  B: 根据模式准备NACK/SACK
```

某次响应丢失时，发送方可能超时后重新发送，因此接收应用还要考虑**同一消息重复到达**，不能见到重复消息就直接认定射频层发送了两条不同内容。

## 5. 抓包应该按什么顺序看？

与《Grant了没声》先看Grant再查Payload类似，短信也要按层拆解：

```text
① 本机确实提交了什么消息？
           ↓
② 实际选择了什么承载？
           ↓
③ 空口有Data Header吗？
           ↓
④ Header CRC/FEC正确、目标和SAP/DPF正确吗？
           ↓
⑤ Blocks to Follow是多少？
           ↓
⑥ 所需Blocks收到几个？有无序号/重复/重传？
           ↓
⑦ Message CRC32是否通过？
           ↓
⑧ 收到相应DLL确认吗？确认和事务匹配吗？
           ↓
⑨ 对端应用解码、入库、UI通知正常吗？
```

可分为下面四个工程“证据门槛”：

| 门槛 | 必须具备的证据 | 失败优先检查 |
|---|---|---|
| Header | DPF、SAP、源/目标、Blocks To Follow、Header CRC | 误识别数据格式、地址、包头损坏 |
| Payload | 接收块数量、纠错/块校验、最终消息CRC | 信道质量、分片丢失、顺序错误 |
| Confirm | 本次事务对应的ACK/NACK/SACK、超时 | 响应收发、超时/重试次数、关联ID |
| Application | 解码结果、应用投递、存储、UI通知 | 字符编码、端口、收件箱与去重 |

**只有“头、块、确认、应用”各层证据完整，才能区分“空口丢”和“应用没显示”。**

## 6. 真实字段应该在哪里看？

以ETSI TS 102 361-1 V2.7.1 §8.2为准：
- Data Header位于Data Type标识的数据头Burst，携带DPF、SAP、地址、Blocks to Follow以及Header CRC等控制信息。
- Confirmed Data Header还包含顺序/片段控制，例如 `N(S)`、`FSN`，并不是简单在Unconfirmed Header上加个“ACK”标志。
- Response Data Header拥有 `Class / Type / Status`，用于报告接收结果。
- Block序号/块CRC和整包CRC属于不同层级的检查，不能用 `fec_ok` 一个布尔变量替代。

建议在解析器中保留原始字节和已归一化字段两套视图：

```c
typedef struct {
    uint8_t dpf;
    uint8_t sap;
    uint32_t src_llid;
    uint32_t dst_llid;
    uint8_t blocks_to_follow;
    bool header_crc_ok;
} dmr_data_header_info_t;
```

这个结构只是日志/分层教学接口，不是逐位等同于ETSI的全部PDU字段；实际产品还需根据不同DPF补充A、SARQ、FSN、N(S)等信息。

## 7. C语言状态机：把“发出去”与“对端收到”分开

下面是一个状态机骨架，不是可直接替代协议的完整实现。

```c
typedef enum {
    MSG_IDLE,
    MSG_QUEUED,
    MSG_TX_ACTIVE,
    MSG_WAIT_DLL_RESPONSE,
    MSG_DLL_CONFIRMED,
    MSG_DLL_REJECTED,
    MSG_TIMEOUT,
    MSG_APP_RECEIPT_CONFIRMED
} msg_tx_state_t;

typedef struct {
    uint32_t local_msg_id;
    msg_tx_state_t state;
    uint32_t deadline_ms;
    uint8_t retries;
    bool require_dll_ack;
    bool require_app_receipt;
} msg_tx_ctx_t;
```

发送事件：

```text
SEND_REQUEST → QUEUED → TX_ACTIVE
                 ↓
       选择是否等待DLL响应
         ├─ Unconfirmed: TX完成后记录“已发出”
         │                不得记“对端已收”
         └─ Confirmed: WAIT_DLL_RESPONSE
                   ├─ ACK: DLL_CONFIRMED
                   ├─ NACK: DLL_REJECTED
                   ├─ SACK: 依据指示重传指定Block
                   └─ Timeout: 按协议重试/报错
```

若产品要求应用送达回执，还应独立维护APP_RECEIPT状态机，与DLL确认相互解耦。UI提示应基于已获得的最高证据级别，不要统一显示“发送成功”。

示例事件日志：

```text
[MSG][TX] local_id=52 queued
[DATA][HEAD] dpf=... sap=... dst=... crc=OK
[DATA][TX] blocks=3 sent=3
[DATA][RESP] expected=YES received=NO timeout
[MSG][TX] result=DLL_TIMEOUT
[UI] status=未确认送达
```

注意：超时阈值和最大重试次数应从对应标准流程/设备配置得出，不能直接把示例的系统tick或任意固定毫秒值当成ETSI统一定时器。

## 8. 四个现场剧本（教学虚构）

### A：发送端有TX_COMPLETE，但对端毫无包头

提示是“已发出”，不能称为“已送达”。先查对端是否处于正确工作信道/资源，目标ID、业务资源和覆盖是否一致。若是Tier III，必要时回查控制面资源分配、业务切换，再抓接收端Data Header。

### B：B收到Header和前两块，第三块CRC失败

这最像分块接收/空口质量问题。检查块序号、纠错结果和Message CRC；Confirmed模式下再看是否返回SACK/NACK、发送方是否按对应事务完成重传。不要先修改短信字符编码。

### C：B完整重组，Message CRC通过，但显示乱码

链路可以正常，应用却不正确。优先核对业务属于哪种文本传输：例如标准IP文本路径是UTF-16BE和通常使用UDP端口5016；厂商私有短信可能采用其他格式。还要检查字节序、消息长度、结尾处理和字体/UI支持。

### D：B已经入库，但收件箱没有弹窗

优先查应用层：收件箱索引、去重ID、联系人过滤、存储空间、事件通知与UI线程。无需因为“用户没看到”就立刻增大发射功率。

## 10. 今天记住这几点

1. **TX完成、DLL ACK、应用收件、用户已读，是四种不同级别的证据。**
2. **Unconfirmed并非一定发送失败，而是该DLL方式不要求对应接收确认。**
3. **Confirmed的ACK/NACK/SACK是数据传送协议语义，不能和Tier III控制面的C_ACKD/C_NACKD Reason混淆。**
4. **短数据可分块，最后的消息CRC与单块纠错/CRC不是同一检查。**
5. **UTF-16BE、推荐UDP 5016只应针对标准IP Text Messaging路径使用；并非所有厂商短信一律如此。**
6. **抓“短信丢了”，先锁定最早丢失证据的层级，再决定查RF还是APP。**

## 11. 自测题

**题1：发送端收到DLL ACK，是否能把UI标记成“对方已读”？**

不能。只能依据协议响应认定对应数据传送完成。用户已读需要应用层明确定义的已读事件。

**题2：短数据头中A=1、SARQ=1，通常说明什么？**

Confirmed短数据，并支持根据响应进行按数据块的选择性重传；仍需遵循Short Data的Stop-and-Wait响应流程。

**题3：接收方整包CRC正确，却显示乱码，第一步查什么？**

首先确认实际短信承载及应用字符编码/端口/字节序，而非直接判断RF链路很差。
