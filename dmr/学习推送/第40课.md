## 3. 阶段 A–E 速通复习（要能一口气说清楚）

每一阶段给你五样：一口气解释、钉子事实、现场易错、回库翻哪篇、以及「若只能留一张纸条写什么」。**不要只背标题。**

### 3.1 阶段 A（第 1–8 课）· 通信地基

**一口气**：无线电把信息装进电磁波发出去；频率是抖多快，带宽是占多宽；DMR 用 **12.5 kHz** 宽的一条「车道」，用 **4FSK** 把比特变成四种频率偏移；多址上 DMR 选 **TDMA 两时隙**，所以同一条车道里能跑两路独立业务；半双工 + 中继/直通是业务形态，个呼/组呼是「找谁说话」。

**钉子**：

1. **频率 ≠ 信道号 ≠ 带宽**——频率是位置，信道间隔是相邻车道间距，带宽是这条信号占多宽。  
2. **4FSK：1 符号 = 2 bit；4800 符号/s → 9600 bit/s**。  
3. **12.5 kHz 车道 + 两时隙 → 业界常说的「6.25 kHz 等效」**（容量口径，不是真把 RF 切成 6.25）。  
4. 模拟对讲是连续波形；数字对讲先量化/编码再调制。  
5. 个呼找一台、组呼找一群——空口最终都落成地址比特。

**易错**：把「听得到」当成「协议对了」；把信道间隔和占用带宽混谈；以为数字对讲不需要天线与覆盖规划；把「数字」理解成「不吃干扰」。

**纸条上只写**：`12.5 kHz · 4FSK · 9600 b/s · 两时隙 TDMA`。


**现场小故事**：新同事把分析仪上的「有能量」当成「DMR 正常」。你带着他看 SYNC：能量在，SYNC 解不出——可能是邻频、模拟残留或 CC 不对。阶段 A 的价值就是：先分清「射频有东西」和「协议有身份」。

**回库**：`学习推送/加餐_频率带宽与调制解调.md`；`00-入门/DMR术语与帧结构速查卡.md`；第 1–4 课原文。

### 3.2 阶段 B（第 9–14 课）· DMR 全貌

**一口气**：DMR 是 ETSI 标准的数字对讲体系；**Tier I** 免执照直通，**Tier II** 执照直通/中继，**Tier III** 带控制器的集群；文档上 **TR 102 398** 讲系统设计，**TS 102 361-1/2/3/4** 分别管空口、语音通用、数据、集群；分层上 L1 物理、L2 链路积木、L3 业务；互操作要看 **SFID / MFID / FLCO** 这几块「门牌」。

**钉子**：

1. Tier 决定「有没有中继 / 有没有 TSCC」，不是决定「是不是 4FSK」。  
2. Part 1 是所有 Tier 的空口底板；Part 4 主要在 Tier III 上场。  
3. 语音 / 数据 / 补充业务是三条业务河，共用同一条空口河床。  
4. 厂商私有功能靠 MFID；标准功能走标准 FID。  
5. `总索引.md` 是「我想查什么」入口，不是按页码读书。

**易错**：把厂商手册当成 ETSI 原文；Tier II 经验直接套 Tier III（缺少登记/Grant 会整段失语）；一上来就啃 Part 4 Annex，地基和空口还糊。

**纸条上只写**：`Tier II=中继 · Tier III=TSCC+Grant · Part1底板 · 总索引检索`。


**现场小故事**：销售材料写「全面支持集群业务」，交付却是 Tier II 中继 + 厂家私有调度。阶段 B 教你先问：有没有 **TSCC**？有没有 **登记 / Grant**？没有前台就不要用 Part 4 的词去承诺 Part 2 的系统。

**回库**：`00-入门/DMR_Tier说明.md`；`DMR整合学习手册.md`；`DMR协议学习导航.md`；`总索引.md` §0–§1；`00-入门/TR102398_V1.5.1_系统设计总览.pdf`。

### 3.3 阶段 C（第 15–24 课）· 空口深入

**一口气**：时间切成 **30 ms** 时隙，两时隙组成 **60 ms** 帧；每个时隙里塞一个突发（约 264 bit）；语音用 **A–F 超帧** 轮转；**CACH** 夹在基站下行缝里捎带路况；**SYNC** 告诉你这是语音还是数据/控制；**Colour Code** 区分同频邻居；**EMB / SLOT / LC / CSBK** 是控制与嵌入信息的积木；FEC 负责「修小错」，学习口径只懂原则、不背矩阵。

**钉子**：

1. **30 ms · ~264 bit · 9600 bit/s** 三者互相咬合——算一算：30 ms × 9600 ≈ 288 bit 量级，扣掉保护与开销后有效载荷落到约 264 bit 这一档（细节以 Part 1 为准）。  
2. 超帧 A–F：语音连续说时的「呼吸节奏」；嵌入 LC 让迟后进入成为可能。  
3. SYNC 是「当前突发身份牌」；认错 SYNC 后面全错。  
4. Colour Code 同频不同网的「小区油漆」。  
5. CSBK / LC 是控制信令的两种常见容器；Tier III 的 C_RAND / C_AHOY / Grant 多数是 CSBK 家族。

**易错**：只看音频好坏不看 SYNC/CC；把 FEC 失败当成「没覆盖」；在分析仪上忽略 CACH；背 FEC 矩阵却说不清「它挂在哪类突发上」。

**纸条上只写**：`先认 SYNC 与 CC，再拆 LC/CSBK；FEC 懂原则即可`。


**现场小故事**：两网同频，用户抱怨「串台」。能量图看起来像干扰，解码一看 Colour Code 不同——有的终端配置错了 CC，有的扫到了邻居。阶段 C 让你相信：**身份牌（SYNC/CC）比音量重要**。

**回库**：`01-空中接口/帧结构与字段定义.md`；`CSBK与LC字段详表.md`；`跳过项原则说明.md`；`AnnexA编址与AnnexH_FID.md`；`00-入门/DMR术语与帧结构速查卡.md`；PDF `TS102361-1_V2.7.1.pdf`。

### 3.4 阶段 D（第 25–30 课）· 语音与数据

**一口气**：一次语音呼叫在空口上大致是「可选预告 → Voice LC Header → 超帧 A–F（嵌入 LC）→ Terminator → Hangtime → Idle」；迟后进入让中途开机的人还能加进来；数据侧有确认/非确认 PDP、短数据与头压缩；查字段时先速览文再回 PDF。

**钉子**：

1. Hangtime 不是「电话还通着」，是「信道还被这次呼叫占着等你续说」。  
2. 迟后进入依赖嵌入 LC / 头信息窗口——和超帧设计绑在一起。  
3. Part 2 管语音与通用服务，Part 3 管分组数据协议。  
4. 「字段文怎么查」本身是技能（第 29 课）：先总索引关键词 → 速览 → PDF 条款。  
5. 第 30 课小综合是 Tier II/通用空口跟读；Tier III 还要在前面加 TSCC 信令。

**易错**：把 Tier II 中继呼叫流程直接当成集群流程；短数据（Part 3）与 UDT（Tier III 控制信道小货车）混名；只会点网管按钮，不会在速览文里定位字段。

**纸条上只写**：`语音=头+A–F+Terminator+Hang；查字段走总索引→速览→PDF`。


**现场小故事**：用户说「电话没挂干净，信道一直被占」。其实是 Hangtime 还在——对方松开 PTT 后系统仍短暂保留信道等续说。阶段 D 把「用户体感」翻译成「空口时间线」，避免误判为死锁。

**回库**：`02-语音业务/语音业务字段速览.md`；`AnnexA定时器.md`；`03-数据协议/数据协议字段速览.md`；对应 Part 2/3 PDF。

### 3.5 阶段 E（第 31–39 课）· 集群 Tier III

**一口气**：集群多了**前台（TSCC）**和**客房（业务信道）**；手台要先**猎站 → 登记（常伴随鉴权）**，打电话先 **C_RAND**，网络用 **Grant** 派客房，用 **Reason** 解释拒绝/排队；频率用 **CHAN**（0 / 1…4094 / 4095）或绝对频率续块；拨号把键盘串映射到 24-bit 地址（Annex E 信息性，Annex G 规范性原生编址）；Stun/Revive/Kill、短信、DGNA 走**控制信道上的管理与 UDT 搬运**，不另占业务信道。

**钉子（务必能默写）**：

| 钉子 | 要点 | 课 |
|------|------|----|
| TSCC vs Payload | 前台发令、客房跑语音/大数据 | 31 |
| 登记 / Aloha | 先被网络认得，才能稳定要业务 | 32 |
| Grant | 成功路径发 Grant（常重复）；失败走 NACK+Reason | 33 |
| Reason | ACK 族里的「为什么」；认码值胜过认中文别名 | 34 |
| 鉴权 | C_AHOY Source=RAND，响应在 ACK；Kill/带鉴权 Stun 有反向考网络；RC4 边界 | 35 |
| CHAN | 0 无效；1…4094 查表；4095=看绝对频率续块；`f = fbase+(CHAN−1)×SEP` | 36 |
| Hunt | 四阶段思路：上次 TSCC → 受令 → 短列表 → 综合扫描；先验证再确认才发射 | 37 |
| 拨号 | NAI‖SSI/SGI；NP=NAI+296 等映射；PSTNI `FFFEC0`；全呼特殊地址；Annex E/G | 38 |
| 管理/UDT | STUNI `FFFECC` / KILLI `FFFECF` / DGNAI `FFFED6` / SDMI `FFFEC5`；UDT 80/176/272/368 bit；DGNA 15+1 | 39 |

**把第 38–39 课几个「门牌地址」再钉一遍**（教学用，不是让你去扫网）：

| 地址 | 名字 | 用途直觉 |
|------|------|----------|
| `FFFEC0` | PSTNI | 外线网关（拨号课） |
| `FFFEC5` | SDMI | 短数据「要货」名义 |
| `FFFECC` | STUNI | 远程暂时禁用/恢复 |
| `FFFECF` | KILLI | 永久禁用（须鉴权） |
| `FFFED6` | DGNAI | 动态组业务台 |

**易错**：Grant 成功却无声——先查 CHAN↔频率表与 CC，再查射频；Reason 当噪声忽略；Stun 后仍见登记以为「没禁上」（Stun 本就保留登记/定位）；组短信「已送达」当成「某人已读」；DGNA Address 模式漏带旧组导致「组丢了」。

**纸条上只写**：`前台要票(Grant)·客房说话·Reason解释拒绝·CHAN是房号不是MHz`。


**现场小故事（三则速记）**：  
1）Grant 成功无声 → 写频缺 CHAN（第 36 课）。  
2）组短信「已送达」投诉 → 组呼不保证个体（第 39 课）。  
3）Stun 后地图仍有点 → 定位保留是设计（第 39 课）。  
阶段 E 的学习成果不是「会背网关地址」，而是**把现象翻译成步骤号**。

**回库**：`04-集群协议/` 下全部速览与专题；尤其 `集群协议字段速览.md`、`ReasonCode与Grant变体.md`、`鉴权与AnnexC频率.md`、`AnnexD猎站Hunt.md`、`AnnexE拨号.md`、`AnnexG本地编址.md`、`Stun_DGNA_UDT与定时器.md`、`Announcement与其余枚举.md`；PDF `TS102361-4_V1.12.1.pdf`。

### 3.6 五阶段速查卡（打印贴墙）

```text
A 地基     12.5kHz | 4FSK | 9600b/s | TDMA两时隙 | 半双工·中继·个呼组呼
B 全貌     TierI/II/III | TR+Part1-4 | L1/L2/L3 | 语音·数据·补充 | SFID/MFID
C 空口     30ms | 264bit | A-F超帧 | CACH | SYNC | CC | EMB | LC | CSBK | FEC原则
D 语音数据  Header→A-F→Term→Hang | 迟后进入 | PDP | 短数据 | 字段文检索技能
E 集群     TSCC/Payload | 登记Aloha | Grant | Reason | 鉴权 | CHAN | Hunt | 拨号 | Stun·DGNA·UDT
```

**阶段之间的「接口」——最容易断的四根线**：

1. **A→C**：会说 4FSK，但不会把 9600 bit/s 和 30 ms 突发对上。  
2. **C→D**：会认 SYNC，但跟不住一次语音呼叫的时间线。  
3. **D→E**：会跟 Tier II 呼叫，但一上 TSCC 就丢掉「先要票再进客房」。  
4. **E 内部**：会 Grant，但 CHAN 表错；或会 Stun，但把组短信语义当已读。

收官自检：挑一根你最容易断的线，用对应两课各重读 20 分钟。

## 4. 一条呼叫：从开机到挂断（课号钉在每一步）

下面用**教学虚构**的手台 M（用户拨号 `40125312` → 空口示例 `0x348E1D`，网号口径沿用第 38 课示例网 NP=401）打一通过程组呼。旁支给出短信与 Stun。

### 4.1 主路径（语音组呼）

```text
[1] 开机 / 掉网恢复
      │  Hunt：上次 TSCC → 受令信道 → 短列表 → 综合扫描
      │  验证 SYScode / CACH → 确认后才允许在该 TSCC 上发射   ← 第37课
      ▼
[2] 守在 TSCC（前台一直在播 Aloha / 广播）              ← 第31、32课
      │  登记（C_RAND 登记类）→ 可能鉴权（C_AHOY RAND ←→ 响应） ← 第32、35课
      ▼
[3] 用户拨号 / 选组 → 映射成 24-bit Target + Service_Options ← 第38课
      │  例：组 40125934 → 0x348217；修饰符进 Service_Options
      ▼
[4] 随机接入：C_RAND（Service_Kind=语音组呼等）         ← 第32、33课
      │  TSCC 可能先 C_AHOY 探可达 / 排队
      │  失败：C_NACKD + Reason（读第34课）
      │  成功：C_GRANT（含 CHAN / 时隙等）反复下发
      ▼
[5] 双方改到业务信道频率
      │  CHAN 1…4094 查本地计划；CHAN=4095 读绝对频率续块   ← 第36课
      │  Colour Code 必须对齐                             ← 第20课
      ▼
[6] 客房里跑语音
      │  Voice Header → 超帧 A–F（嵌入 LC）→ Terminator     ← 第17、25、30课
      │  迟后进入窗口给后来者                              ← 第26课
      ▼
[7] Hangtime 结束 / 网络回收 → 手台回到原 TSCC           ← 第31、25课
```

### 4.2 旁支 · 短信（全程前台，不进客房）← 第 39 课

```text
C_RAND(Target=对方, SK=短数据, 预告块数)
  → C_AHOY(Src=SDMI FFFEC5)「请交货」
  → UDT 上传（C_UDTHU + 1~4 附加块）   # 载荷 80/176/272/368 bit
  → TSCC store-and-forward
  → UDT 下载（C_UDTHD + 块）
  → 个呼回 ACK 并镜像；组呼网络回 Message_Accepted（不保证某人收到）
```

### 4.3 旁支 · 网管远程禁用（Stun）← 第 39 课（网络管理口径）

```text
TSCC 以 STUNI(FFFECC) 发 C_AHOY，Service_Kind=1101，Flag=0
  → 手台停用户业务，仍可登记/漫游/被定位/再收 Revive
Revive：同一套 C_AHOY，Flag=1
Kill：KILLI(FFFECF)，必须先反向鉴权通过；空口不可恢复
```

1. 把 §4.1 主路径抄成一页纸，四个关键课号（37 / 32·35 / 33·34 / 17·25）用荧光笔标出。  
2. 在旁边留三行空白：「本网 TSCC 怎么认」「本网 Reason 高频三个码」「本网 CHAN 计划类型（固定/灵活）」——这三行只能由你的现场参数填写，课程不会也不应替你填真实频率。

### 4.6 短信旁支为什么要单独记

很多人学完集群仍下意识认为「有业务就要进客房」。第 39 课钉死的例外是：

- **短数据 UDT、DGNA、Stun/Revive/Kill**：默认舞台是 **TSCC**。  
- 代价是控制信道容量宝贵 → UDT **最多 4 个附加块**（80/176/272/368 bit 档）。  
- 所以调度规划里，「什么走语音、什么走短信、什么必须上业务信道数据」是容量问题，不是喜好问题。

### 5.8 跨岗位 FAQ（收官高频）

**Q1：我不是开发，还要看 PDF 吗？**  
A：要会「打开到条款核对码值」，不必会实现状态机。速览文够用 80% 场景；争议时才下 PDF。

**Q2：协会 IOP 证书和 ETSI 文本什么关系？**  
A：ETSI 定协议；协会 IOP 测「厂商之间按测试套件互操作」。运营采购常看 IOP，排障仍要回到空口与 Reason。

**Q3：厂商私有功能在课里为什么讲得少？**  
A：因为私有功能靠 MFID，一换厂家就变。标准路径先通，私有能力对照厂商手册，并在分诊时明确「这是标准还是私有」。

**Q4：加餐课和正式课冲突怎么办？**  
A：加餐只加固频率/带宽/调制直觉，不改 ETSI 字段。数字以正式课与 PDF 为准；直觉发糊时回加餐。

**Q5：40 课以后还要「打卡」吗？**  
A：不需要按 9:52/18:52 推送节奏。改用 §10 保养计划：每周症状驱动 30 分钟，每季度返修半天。

## 6. 现场对照与分诊

| 现象 | 先怀疑哪一层 / 哪几课 | 第一刀检查 |
|------|------------------------|------------|
| 开机后一直搜网、发不出去 | Hunt / 写频表 / CC（L37、L36、L20） | TSCC 频率与猎站列表是否一致；能否解码 SYScode |

| 短信「已送达」对方说没有 | UDT 组呼语义（L39） | 个呼还是组呼；组呼只有网络接受义 |

| 「数字机坏了」但模拟同站正常 | 调制/时隙/同步（L4、L15、L19） | 是否真在解 DMR SYNC；别只看 RSSI |

| 新开载频，老终端一派就掉线 | 灵活计划缺行 / SEP 不一致（L36） | 老终端写频是否含该 CHAN |

**分诊口诀**：

> **先空口身份（SYNC/CC），再集群信令（RAND/Grant/Reason），再频率表（CHAN），最后才怪射频硬件。**

再补一句给值班长：

> **网管中文提示是线索，Reason 码值与空口字节才是证据。**

### 6.1 两个完整分诊例子（把表用起来）

**例子 A · 「新载波开通，老批次手台一被派到新信道就掉线」**

1. 分诊表落到：Grant 无声 / 新开载频（L36）。  
2. 打开第 36 课钉子：CHAN 是房号；灵活计划缺行会掉回 TSCC。  
3. 查 `鉴权与AnnexC频率.md`：确认本网是固定还是灵活计划。  
4. 第一刀：抽 2 台老手台读写频，看新 CHAN 是否存在、SEP/CC 是否一致。  
5. 只有写频无误仍失败时，才上频谱/功放硬件。

**例子 B · 「网管点了远程禁用，用户投诉还能看到位置」**

1. 分诊表落到：Stun 后仍见登记/定位（L39）。  
2. 回忆网络管理口径：Stun **保留**定位与登记，停的是用户业务。  
3. 验证标准：该机能否发起/接收语音或短信业务，而不是「网管地图上有没有点」。  
4. 若业务仍能通，再查 C_AHOY 是否真正下发、手台是否回了 MS_Accepted / 不支持类 Reason。  
5. 不要把 Stun 与 Kill 混用；Kill 有反向鉴权与不可恢复语义，权限与流程按运营制度。

### 自测答案

> 答题时尽量写出「课号 + 库文件」——收官考的是检索，不是死背。

1. **12.5 kHz** 是 RF 车道宽；**4FSK** 在车道里用四种偏移装符号；每符号 2 bit、4800 符号/s → **9600 bit/s**；时间上切成 **30 ms** 时隙，使两路 TDMA 共享同一车道。  
2. Tier III 至少多：**守 TSCC、登记（常+鉴权）、C_RAND、等 Grant、再进业务信道**；Tier II 中继通常直接在已知信道上呼叫。  
3. 开机→**Hunt(L37)**→**登记+鉴权(L32/35)**→拨号(L38)→C_RAND→**Grant(L33/34)**→CHAN 调频(L36)→**超帧(L17/25/30)**→Hang→回 TSCC(L31)。  
4. 0：无效/无信道（P_CLEAR 等场景下常表示「回上次 TSCC」类语义，细节以第 36 课为准）；300：逻辑号，查本地计划得 Tx/Rx/CC；4095：不查表，读绝对频率续块。  
5. Grant 只保证「协议上派了房号」；房号→MHz 与 CC 不对，射频再好也解调不到自己的业务。  
6. Reason 在 ACK/NACK/QACK/WACK 等确认族；**Grant 本身不带 Reason**，失败走 NACK 路径。  
7. **不能**。组呼短数据网络侧「接受/已发给组」≠个体送达（第 39 课）。  
8. **不一定失败**——Stun 设计为停用户业务但保留登记/漫游/定位等。Kill 经反向鉴权后永久失去 DMR 功能，空口不可恢复；Stun 可用 Revive（同网关 Flag=1）恢复（第 39 课网络管理口径）。  
9. `鉴权与AnnexC频率.md` 与 `AnnexD猎站Hunt.md`；现场先查老终端写频是否含新 CHAN、CC 是否一致。  
10. SYNC → 突发/数据类型 → Colour Code → CSBK/LC 外壳（再看地址与 Service_Kind）。  
11. **Annex E informative（拨号计划建议）**；**Annex G normative（原生编址能力边界）**。  
12. 总索引当搜索框，学习推送当口语说明书，速览+PDF 当证据。短信投诉例：总索引搜「短数据/UDT」→ 第 39 课 §8 语义 → `Stun_DGNA_UDT与定时器.md` → 需要时回 Part 4 PDF 6.6.4；同时问清个呼还是组呼。

## 晚间深化（2026-10-08）：从一次组呼日志定位到实际 Burst

> 这是第 40 课的晚间补充，不另起第 41 课。午间已经建立协议栈地图；今晚用一条**教学用模拟日志**贯通“空口比特 → 协议解析 → 状态机 → 故障定位”。下文的频率、ID、时间戳均为演示值，不是实测抓包，也不是 ETSI 固定要求的超时时间。

### 1. 先把 30 ms 时隙的 288 bit 与 264 bit 对齐

DMR 4FSK 每个符号 2 bit，4800 symbol/s 即 9600 bit/s。因此一个 30 ms 时隙的时间容量是：

```text
30 ms × 9600 bit/s = 288 bit（时间容量）
一个普通突发 = 108 + 48 + 108 = 264 bit
264 bit / 9600 bit/s = 27.5 ms
余下 2.5 ms 不属于这 264 bit 普通突发内容
```

**不能一律把“余下 24 bit”叫作 CACH**：在典型中继下行时，CACH 占用相关时间位置；而在移动台上行时，需要留出保护、功率爬升和传播时延裕量。方向不同，物理时序用途不同。查规范时要分清 BS outbound 和 MS inbound。

语音 A–F 超帧中，同一时隙每 60 ms 出现一个语音突发。A 突发中部通常为 48-bit Voice Sync；B–F 中部用于嵌入信令，而不是每一个语音突发都放相同的 Voice Sync。每个普通语音突发两侧的 216 bit 可承载 3 个 72-bit 语音编码帧，对应 60 ms 语音。于是：

```text
时刻(ms)       0       60      120     180     240     300
同一业务时隙   A       B       C       D       E       F
中心48bit      SYNC    EMB     EMB     EMB     EMB     EMB
下一组         360ms 再回到 A
```

注意：这是帮助建立节奏的示意；真实突发边界、嵌入字段和交织规则应以 TS 102 361-1 对应格式为准。

### 2. 教学日志：一通 Tier III 组呼怎样穿过协议栈

```text
[00.000][RF]   TSCC RX=450.250000 MHz, RSSI=-67 dBm
[00.060][L1]   TSCC sync acquired, CC=3
[00.180][T3]   C_SYScode verified; quality confirmed
[01.000][UI]   PTT down, target TG=100
[01.030][T3]   Random-access request queued
[01.090][T3]   C_RAND transmitted on permitted access opportunity
[01.270][T3]   Group voice Grant decoded: CHAN=37, TS=2
[01.271][PLAN] CHAN 37 -> MS RX=450.450000 MHz; CC=5
[01.275][RF]   retune start
[01.295][RF]   PLL lock OK
[01.350][L1]   payload sync OK, TS=2, CC=5
[01.410][VOICE] A received; vocoder frames extracted
[01.470][VOICE] B received; embedded signalling collected
[...   ][VOICE] C, D, E, F received

```

这里的时间戳**仅为人为安排的演示顺序**，不能据此实现 Aloha、Grant 等待、PLL 锁定或 T2 的标准定时。真实产品要依据 ETSI 定时要求和射频芯片实测锁定时间设计。

看日志时按层提问：

| 层 | 应该问的问题 | 典型失败证据 |
|---|---|---|
| RF / L1 | 频率正确、符号同步稳定吗？ | RSSI 有，但 Sync 丢失 |
| Burst | 264-bit 边界和数据类型识别对吗？ | 字段错位、FEC/CRC 失败 |
| 控制信令 | C_RAND 发了吗、Grant 解出了吗？ | 等待超时、Reason/NACK |
| 信道规划 | CHAN、TS、CC 是否映射正确？ | Grant 后频率差一个间隔 |
| Voice | A–F 与 LC/EMB 重组正确吗？ | 有同步但音频断续、迟后进入失败 |

### 3. 一段可直接用于嵌入式设计的状态机骨架

不要把 RF 中断里收到的每个 CSBK 都直接解释为“呼叫成功”。应当先校验，再结合当前状态处理事件：

```c
typedef enum {
    T3_SEARCH_TSCC,
    T3_IDLE_ON_TSCC,
    T3_WAIT_ACCESS,
    T3_WAIT_GRANT,
    T3_RETUNING,
    T3_ON_PAYLOAD
} t3_state_t;

typedef struct {
    t3_state_t state;
    uint16_t chan;
    uint8_t slot;
    uint8_t color_code;
    uint32_t rx_hz;
    uint32_t deadline_ms;  /* 工程超时；具体数值不能凭空设为标准值 */
} t3_call_ctx_t;

void on_valid_grant(t3_call_ctx_t *ctx, const grant_t *g)
{
    if (ctx->state != T3_WAIT_GRANT)
        return; /* 非预期时序：记录日志并按协议处理 */

    phy_channel_t phy;
    if (!channel_plan_resolve(g->chan, &phy))
        return; /* 可能是缺失的逻辑信道表或尚待解析的绝对参数 */

    ctx->chan = g->chan;
    ctx->slot = g->slot;
    ctx->color_code = phy.color_code;
    ctx->rx_hz = phy.ms_rx_hz;
    ctx->state = T3_RETUNING;
    rf_request_retune(ctx->rx_hz);
}
```

以上是**接口示意，不是可直接编译的完整协议栈**：`grant_t`、`phy_channel_t` 和 `channel_plan_resolve()` 需由具体工程定义。实际实现还必须处理拒绝、超时、重试、绝对信道参数续块，以及切频后对目标时隙和 Colour Code 的确认。

### 4. 故障演练：Grant 已经收到，为什么还是没声音？

假设出现：

```text
C_RAND TX OK
GRANT RX: CHAN=37 TS=2
RF RX=450.462500 MHz
PAYLOAD SYNC TIMEOUT
```

网络的 Fixed Plan 假设是 `fbase=450.000000 MHz`、`separation=12.5 kHz`，则：

```text
正确：450.000000 + (37-1) × 0.0125 = 450.450000 MHz
错误：450.000000 + 37 × 0.0125     = 450.462500 MHz
```

这是一眼就能识别的 **CHAN-1 错误**。如果频率正确仍不同步，再检查业务信道 CC、TS、PLL 锁定时序、基带同步与信号质量；不要一开始就改 AMBE。

### 今天记住这几点

1. **288 bit 是 30 ms 的理论时间容量，264 bit 才是普通突发的实际调制内容；剩余时间在不同收发方向用途不同。**
2. **Voice A–F 是 6 × 60 ms = 360 ms 的同一时隙语音超帧；A 与 B–F 的中间 48 bit 不应当一概当作相同 Sync。**
3. **Tier III 调试按“TSCC → 接入 → Grant → CHAN/TS/CC → Retune → Payload Sync → Voice”逐级定位。**
4. **状态机中的协议事件、射频完成事件和超时事件必须分开，避免收到 Grant 就错误地认为已经通话成功。**

### 自测题（答案紧随其后）

**题 1：** 30 ms × 9600 bit/s = 288 bit，为什么不能说普通 DMR Burst 就是 288 bit？  
**答：** 普通 Burst 的 264 bit 仅占 27.5 ms，剩余 2.5 ms 的用途依收发方向及突发形式而定。

**题 2：** 同一业务时隙每 60 ms 收到一个语音 Burst，连续 A–F 六个 Burst 覆盖多长时间？  
**答：** 360 ms；每个语音 Burst 通常携带 60 ms 压缩语音信息。

**题 3：** Grant 的 CHAN、TS 已解出，但业务信道同步失败，先查 AMBE 还是先查信道解析？  
**答：** 先查 CHAN→MHz、Colour Code、时隙及切频锁定时序；Payload Sync 没有建立时，AMBE 还不是第一排查点。
