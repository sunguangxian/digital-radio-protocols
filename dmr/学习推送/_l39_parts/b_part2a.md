## 6. UDT：跑在控制信道上的「小货车」

### 6.1 为什么需要它（6.5.0）

规范开门见山：Tier III 业务很多，**搬数据**是普遍需求。UDT 短数据本身是一种主要数据业务，但更多时候是「**为了支撑别的业务**而搬数据」——原文举的例子正是第 38 课那件事：**手台拨 PABX / PSTN 时，要把拨的号码上传给 TSCC**。为了降低 Tier III 的复杂度，**所有经由 TSCC 的数据搬运共用一种方法——统一数据传输机制（Unified Data Transport，UDT）**。

6.5.0 把用途分成三大类：

| 大类 | 原文列出的用途（意译、合并） | UDT 头里的 SF |
|---|---|---|
| **a) 补充数据传输服务** | 上传经网关接通的目的地址、PSTN/PABX 拨号数字、IP 地址、NMEA 位置；下传远端地址、**外线来电号码（CLI）**、IP 地址、NMEA 位置；**作为其他业务一部分的补充用户数据**；呼叫改向的地址/数字；组订阅/附着的组地址上传 | **SF = 1** |
| **b) UDT 短数据投递服务** | NMEA 位置、LIP 位置、**UDT 短信**、**DGNA 的组地址** | **SF = 0** |
| **c) UDT 短数据轮询服务** | 网络向手台要数据 | **SF = 0** |

一句话：**SF = 1 是「给别的业务打下手」，SF = 0 是「我自己就是这次业务的主角」。**短信和 DGNA 都是 SF = 0；拨外线交号码、打电话时顺带传 GPS，是 SF = 1。

### 6.2 一辆货车的结构：1 个车头 + 最多 4 节车厢

```text
 ┌─────────── UDT 头（1 块）────────────┐ ┌附加块1┐ ┌附加块2┐ ┌附加块3┐ ┌附加块4┐
 │ 谁发给谁 · 装什么格式 · 挂几节 · 填几个空 │ │ 数据  │ │ 数据  │ │ 数据  │ │ 数据  │
 └─────────────────────────────────────┘ └──────┘ └──────┘ └──────┘ └──────┘
   车头：C_UDTHD（下行，TSCC→MS）/ C_UDTHU（上行，MS→TSCC）    1~4 节，「必须连续发送」
   DGNA 专用车头：C_DGNAHD / C_DGNAHU
```

UDT 头的 10 个字节（Figure 6.42；下行 Table 7.24、上行 Table 7.28）：

```text
           bit7   bit6   bit5          bit4            bit3..0
Octet 0  │ G/I │  A  │ Emergency/   │ UDT_Option_Flag/ │ Data Packet Format = 0000 │
         │     │     │ Reserved(上行)│ UDT_DIV(上行)     │                           │
Octet 1  │ SAP(4) = 0000（UDT）          │ UDT_Format(4)  ← 装的是什么              │
Octet 2–4│ Target 或网关（24）                                                     │
Octet 5–7│ Source 或网关（24）                                                     │
Octet 8  │ Pad Nibble(5) ← 填了几个 F     │ 0 │ UAB(2) ← 挂几节（值 = 节数 − 1）   │
Octet 9  │ SF │ PF │ Opcode(6)                                                  │
```

| 字段 | 位 | 说人话 |
|---|---|---|
| **G/I** | 1 | 0 = 发给个人；1 = 发给组（**组不回应答**） |
| **A** | 1 | 1 = 要求对方回应答（只对个人有意义） |
| Emergency（下行）/ UDT_DIV（上行） | 1 | 下行：紧急标志；上行：1 = 这个 UDT 装的是**呼叫改向目的地** |
| UDT_Option_Flag（下行） | 1 | 只在「语音/分组数据呼叫顺带补充数据」时有意义（OACSU / FOACSU，Table 7.51）；其他业务填 0 |
| **UDT_Format** | 4 | 车厢里装的是什么（§7.1） |
| **Pad Nibble** | 5 | 最后一节没装满，填了几个半字节的 `1111`（二进制格式填 0） |
| **UAB** | 2 | 挂了几节车厢：`00`=1、`01`=2、`10`=3、`11`=4 |
| **SF** | 1 | §6.1 的那个「打下手」标志 |
| Opcode | 6 | C_UDTHD `011010`（26）、C_UDTHU `011011`（27）、C_DGNAHD `100100`（36）、C_DGNAHU `100101`（37）（Table B.1） |

**和 CSBK 的区别**：C_AHOY、C_ACK 这些是**单块 CSBK**；UDT 是**多块**（头 + 附加块），块结构在 Part 1 定义（6.5.1.1 指向 TS 102 361-1 的 8.2.1.8 / 8.2.2.1 / 8.2.2.5）。在解码器上，你会看到一个「UDT Header」后面紧跟几个「数据块」，而不是一串独立的 CSBK。

### 6.3 两段式：先进仓库，再出仓库

```text
          ┌──── 上传段（upload phase）────┐           ┌──── 下载段（download phase）────┐
 MS(A) ──►│ C_RAND → C_AHOY(要货) → 头+块  │──► TSCC ──►│ 头+块 →（个人）对方回 ACK        │──► MS(B)
          └──────────────────────────────┘   暂存      └───────────────────────────────┘
 MS(A) ◄──────────────────────── 最后：TSCC 把 B 的 ACK 镜像给 A（C_ACKD，Mirrored_Reason）
```

规范图上标了几个**总时长**，给你一个「控制信道上一件小事要多久」的直觉（只引用图上标注的数字，不展开时隙级时序）：

| 规范图 | 场景 | aligned 时序 | offset 时序 |
|---|---|---|---|
| Fig 6.43 | 一条短信（头 + 1 块）从随机接入到对方 ACK | 540 ms | 720 ms |
| Fig 6.44 | 拨外线：上传 ≤20 位号码（头 + 1 块）到 Grant | 270 ms | 390 ms |
| Fig 6.45 | 外线来电：下传来电号码（头 + 1 块）到对方 ACK | 270 ms | 330 ms |
| Fig 6.46 | 打电话顺带上传 GPS（补充数据）再下传 | 450 ms | 660 ms |

> **带宽直觉**（补你的弱项）：一条短信只要半秒多，看起来很快；但这半秒里，控制信道被它占了**七八个突发**（随机接入、AHOY、头、块、再头、再块、ACK……）。控制信道是全站几百台手台**共用的一条 12.5 kHz 车道里的时隙**，如果大家都狂发长短信，登记和呼叫建立就会排队。这就是为什么 UDT **最多 4 节车厢**，也是为什么大批量定位要用更省的 USBD（§10）。

两段之间，TSCC 有两种做法（6.6.4.0 Fig 6.58 的讨论）：**收一块转一块**（端到端延迟小，但上行收错了下行也是错的，白占带宽），或者**整段收完、确认无误再下发**（上行出错可以先重来，但延迟大）。**规范不规定选哪个**（*The timing for the inbound and outbound phases is not prescribed*）——所以不同厂商的短信时延不一样，是正常的。

## 7. UDT 装什么、能装多少

### 7.1 UDT_Format（Table 7.88，Annex B.3）

| 值 | 格式 | 最多装 | 典型用途 |
|---|---|---|---|
| `0000` | 二进制 | 367 bit | 厂商自定义数据、传感器 |
| `0001` | **MS / 组地址** | 15 个 24 位地址 | **DGNA_Address**、网关目的地址 |
| `0010` | **4 位 BCD** | 92 位数字 | **外线号码**（第 38 课）、来电号码 CLI |
| `0011` | ISO 7 位字符 | 52 字符 | 英文短信 |
| `0100` | ISO 8 位字符 | 46 字符 | 西文短信 |
| `0101` | NMEA 位置 | 1 或 2 块 | GPS 位置 |
| `0110` | IP 地址 | IPv4 1 块 / IPv6 2 块 | IP 连接通告 |
| `0111` | **UTF-16BE** | 23 字符 | **中文短信** |
| `1000`/`1001` | 厂商自定义 | — | — |
| `1010` | **混合**（1 个地址 + UTF-16BE） | 1 地址 + 21 字符 | **DGNA_Alias** |
| `1011` | LIP | ≤46 字节 | 定位（格式在 TETRA LIP 标准 TS 100 392-18-1） |
| `1100`…`1111` | 保留 | — | — |

### 7.2 「最多 368 bit」是怎么来的

6.6.4.0 原文：UDT 短数据最多传 **368 bit**；如果是变长二进制，最多 **367 bit**（因为要用 1 bit 标记数据结尾，B.3.1）。来源是车厢尺寸：

```text
非最后一节车厢：12 字节 = 96 bit 用户数据
最后一节车厢：  10 字节 = 80 bit 用户数据（要给块尾的校验留位置）

1 节：           80 bit
2 节：96 + 80  = 176 bit
3 节：96×2 + 80 = 272 bit
4 节：96×3 + 80 = 368 bit   ← 上限
```

套到中文短信上：UTF-16BE 一个汉字 16 bit。1 节 80 bit = **5 个字**；2 节 176 bit = **11 个字**；3 节 = **17 个字**；4 节 = **23 个字**（Table B.8 的 5 / 11 / 17 / 23 正好对上）。**集群控制信道上的一条中文短信，最多 23 个字**——比手机短信短得多，所以现场常见的是「已到达」「请回电」「收到」这种短句，或者干脆用预定义的状态码。

### 7.3 Pad Nibble：最后一节没装满怎么办

字符格式下，最后一节剩下的空位用 **`1111`（DigitNULL）**填满，填了几个半字节（nibble = 4 bit）写在头里的 **Pad Nibble**。查表就行，原理也简单：

```text
Pad Nibble = （这些车厢的总容量 bit − 实际数据 bit）÷ 4
```

| 例子 | 数据 | 节数 / UAB | Pad Nibble | 依据 |
|---|---|---|---|---|
| 「收到」2 个汉字 | 32 bit | 1 节 / `00` | (80 − 32) ÷ 4 = **12** | Table B.8：2 字 → UAB 0、Pad 12 ✓ |
| 「ARRIVED」7 个 ISO 8 位字符 | 56 bit | 1 节 / `00` | (80 − 56) ÷ 4 = **6** | Table B.5：7 字 → UAB 0、Pad 6 ✓ |
| 外线号码 `0112345` 7 位 BCD | 28 bit | 1 节 / `00` | (80 − 28) ÷ 4 = **13** | Table B.3（第 38 课）✓ |
| 12 个 ISO 8 位字符 | 96 bit | 2 节 / `01` | (176 − 96) ÷ 4 = **20** | Table B.5：12 字 → UAB 1、Pad 20 ✓ |

地址格式（DGNA_Address）和二进制格式的 Pad Nibble 固定为 0：地址格式空位填 **ADRNULL `000000`**，二进制格式用「末尾一个 0、后面全 1」来定界（B.3.1）。

**补充数据（SF = 1）的一个例子**（Fig 6.46）：手台打电话时，在 C_RAND 的 Service_Options 里把 **SUPED_SV 置 1**（「我有补充数据要带」），TSCC 用 **SUPLI** 的名义回 C_AHOY 要货，手台上传一节 NMEA 位置，TSCC 再下传给被叫——**被叫回的 ACK 同时兼作「在不在」的检查**，然后才发 Grant。这就是「来电时屏幕上直接显示对方位置」的空口原理之一。

## 8. 从头到尾手拼一条短信「收到」

场景：示例网里，`40125312`（**A**，`0x348E1D`）给同车队的 `40125318`（**B**，`0x348E23`）发一条中文短信「收到」。

### 8.1 第一步：C_RAND 预告（Table 6.55）

```text
9F 00 00 04 34 8E 23 34 8E 1D
│     │  │  └Target=B┘ └Source=A┘
│     │  └ SUPED_VAL=00 | SDATA_VAL=00（1 节） | Service_Kind=0100（个人短数据）→ 0000 0100 = 0x04
│     └ Service_Options 全 0（不带补充数据）+ Proxy=0 → 0x00
└ CSBKO=011111 → 0x9F
```

- C_RAND 的那 4 个「随业务而定」的位，在短数据里拆成 **SUPED_VAL(2) + SDATA_VAL(2)**：前者是补充数据要几节，后者是**短信本身要几节**（值 = 节数 − 1）。  
- 发给**组**就把 Service_Kind 改成 **`0101`**（GRP_SD_SRV），Target 填组号。  
- **目的地址完整写在 C_RAND 里**（6.6.4.3）——这一点和 DGNA 不同（§9.4）。

### 8.2 第二步：TSCC 回 C_AHOY「请交货」

```text
9C 00 00 04 34 8E 1D FF FE C5
         │  └Target=A┘ └Source=SDMI┘
         └ ALS=0 G/I=0 AB=00（交 1 节）SK=0100 → 0x04
```

6.6.4.4 列出主叫可以接受的回应：C_NACKD / C_QACKD / C_WACKD；对方已设置改向时直接回一个 UDT；鉴权用的 C_AHOY（Source = 题目）；**来自 SDMI 的 C_AHOY（要短信本体）**；**来自 SUPLI 的 C_AHOY（要补充数据）**；发往外线等「扩展地址」时，**来自 PSTNI / PABXI / LINEI / DISPATI / IPI 的 C_AHOY（要目的号码）**。如果要发多条，**顺序规定为：ACK 类 → SUPLI → 网关 → SDMI**——先把「附带的」和「去哪」交齐，最后才交正文。

### 8.3 第三步：上传 C_UDTHU + 1 节车厢

```text
头：  40 07 34 8E 23 34 8E 1D 60 1B
      │  │  └Target=B┘ └Source=A┘ │  └ SF=0 PF=0 Opcode=011011（C_UDTHU）→ 0x1B
      │  │                         └ Pad Nibble=12（01100）| 0 | UAB=00 → 0110 0000 = 0x60
      │  └ SAP=0000 | UDT_Format=0111（UTF-16BE）→ 0x07
      └ G/I=0 A=1 Rsvd=0 UDT_DIV=0 | DPF=0000 → 0100 0000 = 0x40

车厢：65 36 52 30 FF FF FF FF FF FF
      └「收」┘└「到」┘ └──── 12 个 F 半字节填充 ────┘
      （「收」= U+6536，「到」= U+5230，UTF-16BE 高字节在前）
```

### 8.4 第四步：下载、应答、镜像

```text
TSCC→B  头：  40 07 34 8E 23 34 8E 1D 60 1A     ← 只有 Opcode 变成 011010（C_UDTHD）
        车厢：65 36 52 30 FF FF FF FF FF FF
B→TSCC  C_ACKU  Reason=0x44 MS_Accepted          （个人短信 + A=1，必须回）
TSCC→A  C_ACKD  A0 00 00 88 34 8E 1D 34 8E 23    ← Mirrored_Reason=0x44；Target=主叫A，AddInfo=目的B
```

下载前 TSCC **可以**先用 C_AHOY 查一下 B 在不在（6.6.4.1.3）；B 回 C_NACKU，TSCC 就放弃并把原因镜像给 A。

**发给组时的三个不同**（6.6.4.1.4 / 6.6.4.5 / 6.6.4.7）：

1. 组成员**收下但不回任何应答**；  
2. TSCC **可以重复下载段**来提高送达率，但**必须等最后一次下载完**才给主叫回最终 ACK；  
3. 主叫收到的是 **Message_Accepted（`0x60`）**，不是 MS_Accepted——意思是「**网络已经发给这个组了**」，**不知道有没有人收到**。

> 所以「组短信显示已送达、对方没收到」**不一定是故障**：可能那台手台当时不在覆盖内、在业务信道上通话没听控制信道、或者正好收错。个人短信才有真正的「对方已收」回执。

**发往外线 / 调度台等「扩展地址」**（6.6.4.0、6.6.4.2）：上传段要做**两次 UDT**——先用 BCD 交目的号码（C_AHOY 来自 PSTNI 等网关，Table 6.54），再交短信正文（C_AHOY 来自 SDMI）。第 38 课的「外线两段式」在短信里又出现了一次。
