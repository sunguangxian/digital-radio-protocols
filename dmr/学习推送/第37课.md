# 第37课：猎站 Hunt——“收到很强的 DMR”为什么还不能驻留？

> 本课目标：理解 Tier III 手台开机后怎样从一组候选频率中找到**真正允许自己驻留的 TSCC**，以及为什么 RSSI 很强、甚至已经能解出 DMR Sync，也不等于“这个站可以用”。

## 1. 先看总流程

上一课已经知道 Grant 中的 CHAN 最终要解析成实际物理频率。今天反过来：手台刚开机时，还没有 Grant，也没有当前 TSCC，它首先必须“找站”。

```text
Power On
   ↓
进入 TSCC Acquisition
   ↓
扫描候选频率 / Hunt List
   ↓
检测到 TSCC Sync？
   ├─ 否 → 下一个候选
   └─ 是
       ↓
   Candidate TSCC
       ↓
   读取 / 校验 C_SYScode
       ├─ 不匹配 → Reject，继续 Hunt
       └─ 允许
           ↓
       Active on TSCC
           ↓
       Signal Quality Check
           ↓
       TSCC Confirmed
           ↓
       才允许进入正常 Random Access / Registration
```

最重要的一句话：

> **“发现 DMR 信号”只是找到候选站；“验证系统身份 + 确认信号质量”以后，才是真正取得 TSCC。**

ETSI TS 102 361-4 把 TSCC acquisition 定义为：先 hunt candidate TSCC，再验证该 MS 是否被允许在选中的 TSCC 上变为 active。手台开机后就应进入这一过程。

## 2. 为什么 RSSI 很强还不够？

假设扫描 450 MHz 附近：

```text
450.125 MHz  RSSI -72 dBm  普通 Tier II
450.250 MHz  RSSI -55 dBm  另一个公司的 Tier III
450.375 MHz  RSSI -68 dBm  本系统 Tier III
```

如果软件只写：

```c
if (rssi > threshold)
    current_tscc = freq;
```

450.250 MHz 会因为最强而胜出，但它可能根本不是本机所属网络。

所以 Hunt 至少有三层判断：

```text
能量存在？
   ↓
是不是符合 TSCC 结构？
   ↓
C_SYScode 是否允许本机驻留？
```

RSSI 只回答第一层。

这和 Wi-Fi 很像：看到一个很强的 AP，不代表它就是你应该连接的那个 SSID。

## 3. Candidate TSCC：Sync 的意义

规范要求 MS 搜索合适控制信道时检查检测到的信号是否符合 TSCC 结构；检测到 TSCC synchronization sequence 后，可以把该信道当作 candidate TSCC。

所以：

```text
RSSI OK
≠ Candidate TSCC

TSCC Sync detected
→ Candidate TSCC
```

注意 Candidate 仍然只是“候选”。

建议代码状态不要从：

```text
HUNT → TSCC_OK
```

直接跳过去，而是：

```text
HUNT
 ↓
CANDIDATE
 ↓
VERIFY_SYS_CODE
 ↓
QUALITY_CONFIRM
 ↓
TSCC_CONFIRMED
```

## 4. C_SYScode 是什么？

可以先把 C_SYScode 理解成 Tier III 控制站广播的“系统身份证”。

它包含用于识别网络/站点的结构信息，例如：

```text
MODEL
NET
SITE
PAR
```

其中 MODEL 决定 NET 和 SITE 的划分方式。DMR 为不同规模网络定义 Tiny / Small / Large / Huge 四种模型。

所以两个站即使：

```text
频率都合法
Colour Code 甚至一样
信号都很强
```

只要 C_SYScode 不符合本机允许的网络/站点条件，就不应该驻留。

## 5. 为什么 CACH 在 Hunt 阶段很有价值？

Part 4 有一个很实用的优化：完整 C_SYScode 是 16 bit，但其中最重要的 14 bit system identity subset 也会通过 CACH 携带；PAR 的两位不在公共 CACH 中。

这意味着 Hunt 时不一定每个候选都要傻等很久：

```text
检测到候选
   ↓
快速解 CACH
   ↓
System Identity subset 明显不匹配
   ↓
立即放弃
   ↓
扫描下一个频率
```

这对嵌入式设备非常重要，因为 Hunt 速度直接影响：

```text
开机到可用时间
掉站后的恢复时间
漫游体验
```

所以 CACH 不只是前面学过的 TDMA/随机接入辅助信息，它在 Tier III 搜站时还能帮助**快速淘汰错误候选**。

## 6. Verification 和 Confirmation 不是一回事

这是实现状态机时最容易偷懒的地方。

当 C_SYScode 已验证、系统允许本机 acquire 后，MS 可以在该 TSCC 上变为 active，然后还要执行 signal quality checking。

因此：

```text
C_SYScode Verification OK
≠ TSCC fully confirmed
```

可以理解成：

```text
Verification：
“身份对，这确实是我要找的网络/站点类型。”

Confirmation：
“而且这个控制信道质量足够可靠，可以真正驻留。”
```

更重要的是：**验证完成但尚未 confirmation 的阶段，MS 不能发送 Random Access PDU。**

这和第32课正好串起来：

```text
Hunt
↓
Verify
↓
Quality Confirm
↓
TSCC Confirmed
↓
Aloha / Random Access
↓
Registration / Call Request
```

所以如果代码一检测到 C_SYScode 就马上发 Registration Request，时序层次是不对的。

## 7. Hunt List 从哪里来？

ETSI 规定了 acquisition 的行为框架，但并不强制厂家只能用一种扫描算法。工程上常见的候选来源可以抽象成：

```text
上次成功驻留的 TSCC
        ↓
邻站/系统提供的候选信息
        ↓
CPS 预配置 Hunt List
        ↓
更宽范围扫描
```

这是非常自然的优化：

如果昨天关机前一直在：

```text
450.375 MHz
```

今天开机先试它，往往比从整个频段最低端开始扫快得多。

但“优先尝试旧频率”不代表可以跳过：

```text
TSCC Sync
C_SYScode
Signal Quality
```

因为网络配置可能已经变化。

## 8. 嵌入式实现建议

状态可以设计成：

```c
typedef enum {
    T3_HUNT_START,
    T3_HUNT_TUNE,
    T3_HUNT_SYNC,
    T3_HUNT_VERIFY_SYS,
    T3_HUNT_QUALITY,
    T3_TSCC_CONFIRMED
} t3_hunt_state_t;
```

候选记录：

```c
typedef struct {
    uint32_t freq_hz;
    int16_t  rssi;
    bool     sync_ok;
    bool     syscode_ok;
    bool     quality_ok;
} t3_candidate_t;
```

注意不要把 RSSI 直接作为最终判定：

```c
/* 错误思路 */
best = strongest_rssi_channel;

/* 更合理 */
best = strongest_valid_confirmed_tscc;
```

也就是说：

> **先判断“合法”，再在合法候选中比较“质量”。**

## 9. 一个典型现场 Bug

现象：

```text
实验室只有一个基站：
开机 1 秒驻留成功。

客户现场多个 DMR 系统：
开机有时 10 秒以上，偶尔驻留错误。
```

如果 RF 灵敏度没有明显问题，优先检查：

```text
Hunt List 顺序
↓
错误候选淘汰是否太慢
↓
CACH identity subset 是否利用
↓
C_SYScode MODEL/NET/SITE/PAR 解析
↓
候选超时是否过长
↓
Signal Quality confirmation
```

特别是这种写法：

```c
if (dmr_sync_found)
{
    wait_full_timeout();
    try_decode_everything();
}
```

可能让每个错误 DMR 候选都浪费大量时间。

更好的策略是尽可能早地利用协议字段做 early reject。

## 10. 日志建议

建议把 Hunt 日志做成一条清晰的流水线：

```text
[T3][HUNT] TRY
FREQ=450.250000 MHz

[T3][HUNT] SYNC OK
RSSI=-55

[T3][HUNT] SYSCODE
MODEL=...
NET=...
SITE=...
RESULT=REJECT

[T3][HUNT] NEXT
FREQ=450.375000 MHz
```

正确候选：

```text
[T3][HUNT] SYNC OK
[T3][HUNT] SYSCODE OK
[T3][HUNT] QUALITY OK
[T3][HUNT] TSCC CONFIRMED
```

这样“搜不到站”和“搜到了错误站”会变成两个完全不同的问题。

## 今天记住这几点

1. **RSSI 强，只说明这里有较强 RF 能量，不说明它是本机应该驻留的 TSCC。**
2. **检测到 TSCC Sync 后只是 Candidate TSCC。**
3. **C_SYScode 用来识别/验证网络和站点；MODEL、NET、SITE、PAR 是理解它的核心入口。**
4. **CACH 中携带的 System Identity subset 可以帮助 Hunt 时快速淘汰错误候选。**
5. **Verification OK 以后还要做 signal-quality confirmation。**
6. **TSCC 未确认前不能进行 Random Access。**
7. 工程实现应优先“快速拒绝错误候选”，否则多系统 RF 环境下开机搜站会明显变慢。

## 自测题

**1. 扫描到 -50 dBm 的 DMR 信号，而另一个候选只有 -70 dBm，应该直接驻留 -50 dBm 吗？**

不应该。先确认它是否为合法 candidate TSCC，并校验 C_SYScode；只有在合法候选之间，信号质量比较才有意义。

**2. 已经正确解出 C_SYScode，能立即发送 Registration Request 吗？**

不能简单这么做。系统身份验证后还要完成 TSCC confirmation / signal-quality checking；在 verification 后、confirmation 前，规范明确禁止 MS 发送 Random Access PDU。

**3. 为什么 Hunt 阶段也值得认真解 CACH？**

因为 CACH 携带 C_SYScode 的重要 identity subset，错误网络可以更早被淘汰，从而缩短整体 Hunt 时间。
