# DMR 第 25 课：一次语音呼叫到底怎么走——从 PTT 到松键

前面 24 课我们把 Burst、SYNC、CACH、Colour Code、Slot Type、EMB、Full LC、CSBK 和 FEC 分开学了。从今天开始把它们重新装回一条真实链路。

> 本课最重要的目标：以后看到空口日志时，不再只认“某个字段”，而是能判断“当前处于一次语音呼叫的哪个阶段”。

## 1. 先看总时序

以 Tier II 中继模式、组呼为例，移动台 A 呼叫 TG100：

```text
按下 PTT
   │
   ├─ 入站：接入/同步
   │
   ▼
Voice LC Header
   │
   ▼
Voice A
   ▼
Voice B
   ▼
Voice C
   ▼
Voice D
   ▼
Voice E
   ▼
Voice F
   │
   ├─ A→F 周期重复
   │
松开 PTT
   │
   ▼
Terminator with LC
```

中继台在对应 outbound slot 上转发这次呼叫，同时 CACH 持续提供 TDMA/CACH 相关控制信息。

这里有三个阶段：

```text
呼叫建立：Voice LC Header
呼叫持续：Voice A～F Superframe
呼叫结束：Terminator with LC
```

这三个阶段先记牢。

## 2. 为什么一按 PTT 不能直接发 AMBE 语音？

因为接收机必须先知道“这是谁的呼叫”。

例如：

```text
SRC = 10001
DST = TG100
Call Type = Group Voice
```

如果直接送 AMBE：

```text
AMBE → AMBE → AMBE ...
```

接收端虽然可能解出声音，却不知道：

- 谁在讲话；
- 是个呼还是组呼；
- 目标组是谁；
- 是否应该打开本机扬声器。

所以语音 Payload 前需要控制信息。

这就是 Voice LC Header 的价值。

## 3. Voice LC Header 为什么长得像 Data Burst？

这是前几课非常关键的知识点。

Voice LC Header 虽然服务于“语音呼叫”，但空口承载使用 general data burst 结构：

```text
98 bit | Slot Type | Data SYNC | Slot Type | 98 bit
```

Slot Type 解出来后：

```text
CC = 当前系统 Colour Code
Data Type = Voice LC Header
```

随后：

```text
196 coded bits
      ↓
BPTC(196,96) Decode
      ↓
96 bit
      ↓
LC + CRC
      ↓
Full LC
      ↓
SRC / DST / FLCO ...
```

因此抓包看到：

```text
Data SYNC
Data Type = Voice LC Header
```

并不代表“现在在发用户数据”。

它只是说明：

> 这一个控制 Burst 使用了 Data Burst 的物理格式。

## 4. Voice A 为什么特别？

Voice LC Header 后开始真正语音。

Voice A 的典型中心结构是：

```text
108 bit Voice
+
48 bit Voice SYNC
+
108 bit Voice
```

所以 A 帧承担一个非常重要的作用：

> 给接收机提供明确的 Voice SYNC，并帮助建立语音超帧相位。

接收端检测到 Voice SYNC 后，可以建立：

```text
现在是 A
下一帧应该是 B
再下一帧 C
...
直到 F
然后重新 A
```

因此你的代码最好有一个明确的 superframe phase：

```c
typedef enum {
    DMR_VOICE_A,
    DMR_VOICE_B,
    DMR_VOICE_C,
    DMR_VOICE_D,
    DMR_VOICE_E,
    DMR_VOICE_F
} dmr_voice_phase_t;
```

不要仅靠“收到第几个包”隐式推断。

## 5. B～F 为什么不继续放 Voice SYNC？

因为中心 48 bit 很宝贵。

A 用它做：

```text
Voice SYNC
```

而 B～F 要利用这个位置携带：

```text
EMB + Embedded Signalling + EMB
```

因此可以形成这样的直觉：

```text
A：重新告诉你“语音超帧在这里”
B～F：利用已建立的相位，顺便发送控制信息
```

这也是为什么语音和数据的同步策略不同。

Data Burst 可以频繁使用 Data SYNC；连续 Voice Burst 则把部分中心资源让给 Embedded Signalling。

## 6. B～F 中的 EMB 在做什么？

EMB 的核心有效信息包括：

```text
Colour Code
PI
LCSS
```

其中你最近重点学过：

```text
CC
→ 这是我的系统吗？

LCSS
→ Embedded LC 分片处于什么关系？
```

所以 B～F 不是简单的：

```text
Voice Payload + 一点无关数据
```

而是同时存在两条逻辑路径：

```text
Voice Payload
   ↓
AMBE Decode
   ↓
Audio

Embedded Signalling
   ↓
LC重组
   ↓
Call Context
```

因此现场完全可能出现：

```text
声音正常
但联系人/呼叫信息异常
```

这时不要第一时间怀疑 AMBE。

## 7. 为什么已经有 Voice LC Header，还要 Embedded LC？

因为“迟后进入”。

假设 A 已经讲话 5 秒：

```text
LC Header
A B C D E F
A B C D E F
A B C D E F
...
                    ↑
              B 此时才切到信道
```

B 已经错过最开始的 Voice LC Header。

如果后面永远只发语音，它可能知道：

```text
这里有 Voice
```

却缺少完整呼叫上下文。

因此持续语音期间会通过 Embedded Signalling 重复携带 Link Control 信息。

这样迟到的终端仍有机会恢复：

```text
SRC
DST
Call Type
...
```

所以 Embedded LC 不是“多余重复”，而是提高持续呼叫中的可加入性和鲁棒性。

## 8. A～F 到底多长？

每个 TDMA burst 的占用窗口约 30 ms，但同一时隙的 burst 是隔一个时隙出现的。

可以画成：

```text
时间 →

TS1        TS2        TS1        TS2
30 ms      30 ms      30 ms      30 ms
  A                     B
```

对于同一个逻辑时隙：

```text
A → 约60 ms → B → 约60 ms → C ...
```

所以 A～F 六个 voice burst 构成的 superframe 周期约：

```text
6 × 60 ms = 360 ms
```

这也是为什么 Voice SYNC 不需要每 30 ms 出现一次：对同一逻辑信道而言，A 周期性提供重新同步机会。

## 9. 松开 PTT 后为什么还要 Terminator with LC？

如果发射机直接停止 RF，接收机只能靠超时判断：

```text
“是不是呼叫结束了？”
```

这不够明确。

所以正常结束会发送 Terminator with LC。

你可以先把它理解成：

```text
Voice LC Header
≈ begin-call control

Voice A～F
≈ call body

Terminator with LC
≈ end-call control
```

它同样携带 Link Control，使接收端能够明确完成一次呼叫的收尾。

接收状态机因此可以：

```text
IDLE
 ↓ LC Header
CALL_ACTIVE
 ↓ Voice A～F
CALL_ACTIVE
 ↓ Terminator
IDLE
```

## 10. 一次组呼在软件里建议怎样分层？

建议至少拆成：

```text
RF / Modem
↓
Burst Detector
↓
SYNC / Burst Type
↓
Slot Type / EMB
↓
FEC
↓
LC / Voice Parser
↓
Call State Machine
↓
Audio / UI / RSC
```

尤其不要让“收到一个 Voice A”直接驱动所有业务。

可以设计事件：

```c
DMR_EVT_CALL_HEADER
DMR_EVT_VOICE_BURST
DMR_EVT_EMBEDDED_LC
DMR_EVT_CALL_TERMINATOR
```

上层 Call State Machine 再维护：

```c
typedef struct {
    uint32_t src_id;
    uint32_t dst_id;
    uint8_t  call_type;
    uint8_t  slot;
    uint8_t  colour_code;
    bool     lc_valid;
} dmr_call_ctx_t;
```

这样以后做中继、RSC、联系人显示、录音、迟后进入都会清晰很多。

## 11. 推荐的调试日志

一次正常呼叫最好能看到类似：

```text
[RX] DATA_SYNC
     DT=VOICE_LC_HEADER
     CC=1
     SRC=10001
     DST=100

[RX] VOICE_A
     VOICE_SYNC OK

[RX] VOICE_B
     EMB CC=1
     LCSS=...

[RX] VOICE_C
     EMB CC=1
     LCSS=...

[RX] VOICE_D
     ...

[RX] EMB_LC COMPLETE
     SRC=10001
     DST=100

[RX] VOICE_F

...

[RX] DATA_SYNC
     DT=TERMINATOR_WITH_LC
     SRC=10001
     DST=100

[CALL] END
```

这类日志比只打印：

```text
RX voice
RX voice
RX voice
```

有价值得多。

## 12. 现场问题怎么从时序反推？

### 情况 A：完全不开音

先看：

```text
SYNC？
CC？
TS？
LC Header？
DST 是否匹配？
```

### 情况 B：声音正常，但联系人偶尔不显示

重点看：

```text
LC Header
Embedded LC
LCSS
Embedded FEC
```

### 情况 C：开头正常，但迟后进入失败

重点看：

```text
Voice A～F phase
EMB
LCSS
Embedded LC reassembly
```

而不是只查 Voice LC Header。

### 情况 D：松键后 UI 很久才退出呼叫

重点看：

```text
Terminator with LC
Call State Machine
Timeout fallback
```

这就是把协议知识变成调试方法。

## 今天记住这几点

1. 一次正常语音呼叫可以先记成：

```text
Voice LC Header
→ Voice A～F
→ A～F重复
→ Terminator with LC
```

2. Voice LC Header 服务语音呼叫，但使用 general data burst 格式，所以看到 Data SYNC 是正常的。

3. Voice A 通过 Voice SYNC 建立/恢复超帧相位；B～F 的中心位置主要用于 Embedded Signalling。

4. Embedded LC 的重要意义之一是支持迟后进入：错过开头 LC Header 的终端仍有机会恢复呼叫上下文。

5. 同一逻辑时隙的 Voice Burst 约每 60 ms 出现一次，A～F 六个 Burst 的 superframe 约 360 ms。

6. Terminator with LC 是明确的呼叫结束控制，不应该只依赖“RF 消失 + 超时”。

## 自测题

### 1. 为什么 Voice LC Header 明明属于语音呼叫，却会出现 Data SYNC？

因为它使用 general data burst 物理格式承载 Link Control；业务类型是语音，不等于每一个相关 Burst 都必须使用 Voice SYNC。

### 2. 如果终端在呼叫开始 3 秒后才切到该信道，它已经错过 Voice LC Header，为什么仍可能正确显示主叫和组号？

因为持续语音中的 Embedded Signalling 会周期性提供 Link Control 信息，接收端可以通过迟后进入重新建立呼叫上下文。

### 3. 如果声音一直正常，但迟后进入时经常没有联系人信息，优先检查 AMBE 吗？

不是。优先检查 A～F 相位、EMB、LCSS、Embedded LC 分片重组和相关 FEC。
