
## 6. 完整例子

### 例子 A · 同频两中继，靠 CC 分开

园区只有一对许可频率。安保中继与后勤中继**输出同频**，覆盖有重叠。

- 安保：CC=**3**，TS1 跑安保组；  
- 后勤：CC=**9**，TS1 跑后勤组。  

手台若误写成 CC=9 却想听安保：可能「有数字味道 / 分析仪能看到邻系统 SYNC」，但本机不当安保话务。  
若两人**都误写成同一个 CC=3**：同频叠扰 + 系统边界塌掉，现场会像「串台升级版」。

要点：**CC 是系统色，不是组名。** 组仍要另配 Talkgroup。

### 例子 B · 写频事故：SYNC 漂亮，CC 写错

用户投诉：「中继灯在闪，同事说听得到我，我听不到他们。」

分析仪对用户机旁接收：出站 **Voice SYNC** 稳定，Slot Type/EMB 解出 **CC=1**；  
用户写频却是 **CC=2**。

路径：

1. SYNC 成功 → 壳没问题；  
2. CC 不匹配 → 静噪/业务过滤把话挡在门外；  
3. 改回 CC=1 → 恢复。  

这就是「**壳对了、色不对**」的标准剧本。

### 例子 C · 分析仪读 CC，规划员对表

规划员用分析仪扫一段已知同频走廊：

- 频点 X 上交替出现 **CC=4** 与 **CC=11** 的突发；  
- 说明至少两套色在共用/挤占该频。  

动作：画覆盖与色码复用图；确认两套是否故意同频异色；检查是否有第三家误用了其中一色。

### 例子 D · 直通 All site（小心讲）

车队近距离切直通测试。某台显示色码 **15**，手册/规范语汇对应 DM **All site（`1111`）**。

讲解口径：

- 这是 **Direct Mode** 下的特殊取值语义；  
- 不要直接拿去「对齐园区中继的日常 CC」；  
- 测试记录写清「DM / All site」，避免运维同事当成中继色码事故。

### 例子 E · 「像错组」其实是错色

用户说：「怎么变成别的对讲组了？」  
实际：邻系统同频、用户 CC 误写成邻系统色，听到的是**邻系统当前话务**；Talkgroup 显示也可能让人产生「组乱了」的错觉。

分诊：先对 **CC 与系统名**，再对组列表——避免在错误系统里疯狂改组。

## 7. 数字账本

| 量 | 值 / 关系 | 别和谁混 |
|----|-----------|----------|
| **CC 位宽** | **4 bit** | ≠ 48 bit SYNC；≠ 24 bit CACH |
| **色码个数** | \(2^4=\)**16**（CC0–CC15） | 不是「无限系统 ID」 |
| **All site（DM）** | **`1111`₂ = 15** | 见 §4.4；以 9.3.1 为准 |
| **Slot Type** | **20 bit** = 8 信息 + 12 校验 | 信息里含 CC(4)+Data Type(4) |
| **EMB** | **16 bit** = 7 信息 + 9 校验 | 信息里含 CC(4)+PI+LCSS |
| **SYNC** | **48 bit** 中心图案 | **不含** CC 字段 |
| **CACH** | **24 bit** 缝 | 主场 AT/TC/LCSS；别默认当 CC 柜 |
| **Traffic** | **264 bit** | 货箱总长 |
| **带宽 / 调制** | **12.5 kHz** + **4FSK** | CC **不改变**二者 |
| **校验名（记名即可）** | Slot Type: Golay(20,8)；EMB: QR(16,7,6) | 不贴矩阵；实现以 PDF Annex B 为准 |

分柜口诀：

```text
264 货箱
 ├─ 中心 48 …… SYNC 或 嵌入窗
 │                ├─ SYNC …… 认壳（无 CC）
 │                └─ EMB+碎片 …… EMB 内有 CC
 ├─ 数据壳两侧 Slot Type …… 内有 CC + Data Type
 └─ 缝 24/Guard …… CACH 故事（第 18 课）
```

## 8. 常见误区（10 则）

1. **「Colour Code 就是 SYNC。」** → 否。SYNC 是中心 48 图案；CC 在 Slot Type / EMB。  
2. **「Colour Code 就是 CACH。」** → 否。CACH 在出站缝；CC 不在那条主故事里。  
3. **「Colour Code 就是 Talkgroup。」** → 否。规范写明 CC 不做个呼/组呼寻址。  
4. **「SYNC 成功 = 色码一定对。」** → 否。本课核心反例。  
5. **「改色码会换频率/换调制。」** → 否。仍是 12.5 kHz + 4FSK。  
6. **「CC 不同就完全没有射频干扰。」** → 否。拒收≠消能量；强邻频/同频仍可能抬噪、砸解调。  
7. **「CC 等于加密/保密。」** → 否。匹配只是系统色标过滤；明文话务仍可能被监视类接收机看到。  
8. **「十六个色码不够用就重复没关系。」** → 同频覆盖重叠时重复很危险；要靠规划复用距离。  
9. **「同步不上 = 先改 CC。」** → 顺序常反：先 SYNC/射频，再 CC，再组与业务。  
10. **「直通 CC=15 就当普通第 15 号色去对中继。」** → 先核对 DM **All site** 语义（9.3.1）。

## 9. 自测（8 题）

**题 1.** Colour Code 主要出现在哪些 PDU/场？它和 Traffic 中心 48 的 SYNC 图案是同一段吗？

<details><summary>简答</summary>

主要在 **Slot Type（数据/控制突发）** 与 **EMB（语音嵌入信令）**。SYNC 是中心 **48 bit 图案**，**不是** CC 字段本身。二者常「前后相关」，但不是同一段比特。

</details>

**题 2.** CC 有多少 bit？有多少种取值？Direct Mode 里 `1111` 叫什么？

<details><summary>简答</summary>

**4 bit** → **16** 种（CC0–CC15）。DM 中 **`1111` = All site**（资料库 / Part1 **9.3.1**）。讲解时要标明「直通特殊语义」，勿与日常中继色码口语混用。

</details>

**题 3.** 为什么说「SYNC 成功 ≠ CC 匹配」？举一个现场症状。

<details><summary>简答</summary>

SYNC 只说明中心图案/壳边界对上了；CC 是另一次系统色匹配。典型症状：分析仪有 Voice/Data SYNC，RSSI 不差，但本机无声或不当本系统——写频 CC 与空口 CC 不一致。

</details>

**题 4.** 同频两套系统应如何使用 Colour Code？若误用同一 CC 会怎样？

<details><summary>简答</summary>

应使用**不同 CC**，降低误听/误转、便于检测同频干扰。误用同一 CC：系统边界塌掉，更容易互相当自己人，叠加物理干扰，排障极难。

</details>

**题 5.** 用一张表对比 SYNC、Colour Code、CACH（位置 / 长度 / 干什么）。

<details><summary>简答</summary>

| | 位置 | 长度 | 干什么 |
|--|------|------|--------|
| SYNC | Traffic 中心 | 48 bit | 认壳、对齐、分语音/数据等 |
| CC | Slot Type / EMB 内 | 4 bit | 同频系统色标 |
| CACH | 出站缝 | 24 bit | 忙闲、槽号、短 LC 等 |

</details>

**题 6.** 用户说「有信号没声音」。你按什么顺序问三件事？

<details><summary>简答</summary>

建议序：① 频点/时隙/射频是否够；② **Colour Code** 是否与系统一致；③ 组地址/业务/是否误开监视。并提醒：有能量 ≠ 已 SYNC ≠ CC 已匹配。

</details>

**题 7.** Colour Code 会改变 12.5 kHz 或 4FSK 吗？它是不是 Talkgroup？

<details><summary>简答</summary>

**不会**改变带宽/调制。也**不是** Talkgroup——规范明确 CC 不做个呼/组呼寻址。

</details>

**题 8.** 数据壳里 Slot Type 除了 CC 还有什么？语音超帧 A 的中心通常是 CC 吗？

<details><summary>简答</summary>

Slot Type 还有 **Data Type**（及 parity）。超帧 **A** 中心通常是 **Voice SYNC 图案**，不是「SYNC 里直接等于 CC」；语音过程中的 CC 要到 **EMB**（及前后数据单据的 Slot Type）上读。

</details>
