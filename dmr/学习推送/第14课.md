# 第 14 课 · 互操作：SFID / MFID / FLCO

> DMR 深入学习 · 阶段 B 全貌（互操作收官课）  
> 适合：已能分清语音/数据/补充业务，但一听到「特性集」「SFID」「厂商私有 FID」「FLCO」就晕——分不清「同频同色码为啥还各说各话」、标准业务该挂哪个门牌的人  
> 阅读量：约 30–40 分钟 · 几乎不推公式 · 要把「FID = 特性集门牌、FLCO/CSBKO = 门牌下的功能码、标准业务必须走 SFID」钉死  
> 若频率/带宽/调制仍糊：只提醒一句——坏射频常**看起来像**「互操作失败」，其实是 L1 听不清；互操作真正卡在 **FID + Opcode**。频谱加餐见 `学习推送/加餐_频率带宽与调制解调.md`。本课主线是**特性互操作**，不重讲频谱。

## 1. 为什么本课重要（动机）

第 13 课钉死了业务全景：Bearer / Tele-service / Supplementary；语音主战场在 Part2，数据在 Part3，集群控制信道短数据还要看 Part4。下一关不是再背菜单，而是学会**把「用户要的能力」钉到空口门牌上**：

- 采购说「两家 DMR 都符合标准，应该能互通」，联调时 A 厂组呼正常、B 厂「特色导航语音」对端完全听不见——不是天线坏了，而是 **MFID 私有特性**对端不认。  
- 抓包看到 Full LC 的 `FID=0x00`、`FLCO=000000`，同事问「这是什么」——这是标准组呼语音信道用户 LC；若 `FID` 落在厂商区，同一 `FLCO` 数值**含义可能完全不同**。  
- 产品经理要求「把标准个呼做成我们自己的 Opcode，好防拷贝」——这会直接破坏互操作：规范要求**已标准化的特性只能经 SFID + 对应 FLCO 暴露**。  
- 对端回了一条「Feature Not Supported（FNS）」类信令——不是骂你，是礼貌地说「你用 SFID 叫了一个我不支持的标准 Opcode」。  
- 产业侧还有 **DMR Association IOP 认证**：测的是标准特性清单能否互通；私有特性本来就不在「必通」名单里。

若只背「DMR 能互通」五个字，后面会卡在同一处：

> **互操作不是「都写着 DMR 就能说话」。空口上先看 FID（哪一套特性集），再看 FLCO/CSBKO（这套里的哪一个功能）。标准业务挂 SFID；厂商私活挂 MFID。门牌挂错，同频同色码也会各说各话。**

本课目标是让你能自己讲清十件事：

1. **为什么**要用「商场门牌 + 楼层功能码」来记 SFID/MFID/FLCO；  
2. 一张总图：FID 分区（Table H.1）+ Full LC / CSBK 外壳里的位置；  
3. 白话术语：FID、SFID、MFID、FLCO、CSBKO、FNS、IOP；  
4. 现场岗位与故障如何映射到「查 FID 还是查射频」；  
5. SFID 下常见 FLCO / CSBKO 地图（与第 13 课业务对照）；  
6. 完整例子：标准组呼 vs 厂商私有 LC vs FNS；  
7. 数据侧 Part3 的互操作提醒（第二数据头 / MFID）；  
8. 常见误区 + 自测；  
9. 资料库加深阅读路径；  
10. 为阶段 C「时隙 30 ms」留下钩子（本课收官阶段 B）。

## 2. 总图 / 故事：商场门牌 + 楼层功能码

先把整课装进「商场导航」故事，再落到 Part1 Annex H 与 Part2 clause 4.3。精神与 `DMR整合学习手册.md` §5.1、`AnnexA编址与AnnexH_FID.md` 一致。

### 2.1 商场门牌故事（直觉）

想象空口上每个「控制/链路控制」消息都要先报门牌，再报楼层服务：

```text
┌─────────────────────────────────────────────────────────────┐
│  FID（8 bit）= 商场门牌 / 特性集                              │
│     0x00 = SFID「标准馆」——Part2/Part3 写明的默认特性集        │
│     厂商区 = MFID「某某品牌私密馆」——对端未必有钥匙             │
│                                                             │
│  FLCO（6 bit，在 Full LC 里）= 该馆内的空中功能码              │
│     例：标准馆里 000000 = 组呼语音信道用户                      │
│                                                             │
│  CSBKO（6 bit，在 CSBK 里）= 控制信令块上的功能码              │
│     例：标准馆里 000100 = 个呼语音业务请求                      │
└─────────────────────────────────────────────────────────────┘
```

类比要落地到机制：

| 商场说法 | 真实机制（请用这句对外讲） |
|----------|----------------------------|
| 「门牌」 | **FID**：标识用的是哪一套特性集 |
| 「标准馆」 | **SFID** = `00000000`（0x00）：TS 102 361-2 默认特性集 |
| 「品牌私密馆」 | **MFID**：厂商向 ETSI 申请的特性集；对端不懂就不处理 |
| 「馆内服务码」 | **FLCO**（Full LC）或 **CSBKO**（CSBK）：该 FID 下的空中功能 |
| 「对不起，本店不提供」 | **FNS**（Feature Not Supported）：被个呼到、但不支持该 SFID+Opcode |

口诀：**先看门牌（FID），再看服务码（FLCO/CSBKO）。标准业务只能开在标准馆。**

### 2.2 为什么「同频同色码」还不够

同频、同 **12.5 kHz** 信道间隔、同 Colour Code、甚至同个呼/组呼号码，只保证「听得到比特、不会误入别的系统」。**听懂业务意图**还要门牌一致：

```text
射频层 OK（12.5 kHz · 4FSK · 30 ms 时隙）
        │
        ▼
   L2 解出 Full LC / CSBK 外壳
        │
        ├── FID == 0x00 且 FLCO/CSBKO 是标准表里的？
        │         → 按 Part2/Part3 解释（可互通）
        │
        └── FID 落在 MFID 区？
                  → 只有支持该厂商特性集的设备才「懂」
                  → 其他厂设备通常静默忽略（不是天线坏了）
```

### 2.3 规范总图（请在脑子里贴墙上）

```text
                    ┌──────────────────────────────┐
                    │  用户要的能力：组呼 / 个呼 / 别名 / 私有导航… │
                    └──────────────┬───────────────┘
                                   │
                    ┌──────────────▼───────────────┐
                    │  是否已在 Part2（或 Part3）标准化？ │
                    └──────┬─────────────────┬─────┘
                           │是               │否
                           ▼                 ▼
                    必须用 SFID          只能用 MFID
                    + 标准 FLCO/CSBKO    + 厂商自定 Opcode
                           │                 │
                           └────────┬────────┘
                                    ▼
                         Full LC / CSBK 外壳里写出
                         Octet0: … Opcode(6)
                         Octet1: FID(8)
```

Annex H 分区摘要（学习用；冲突以 PDF 为准）：

| FID 值（二进制直觉） | 含义 |
|----------------------|------|
| `00000000` | **SFID** — TS 102 361-2 标准业务 |
| `00000001`…`00000011` | 保留，未来标准化 |
| `00000100`…`01111111` | **MFID** 厂商区 |
| `1xxxxxxx` | 保留，未来 MFID 扩展 |

要点：一家厂商可持有多个 MFID；多家也可共用同一 MFID（厂商策略）。MFID **向 ETSI 申请**（见 Part1 Annex H.2）。

贯穿数字（舞台仍是空口，阶段 C 会拆时隙）：

| 项 | 值 | 互操作直觉 |
|----|-----|------------|
| 信道间隔 | **12.5 kHz** | 「地皮」一样，不保证「店规」一样 |
| 时隙 | **30 ms** | 比特按时到达，不等于 Opcode 同义 |
| FID | **8 bit** | 门牌 |
| FLCO / CSBKO | **各 6 bit** | 门牌下的功能码 |
| SFID | **0x00** | 标准馆唯一默认门牌 |

## 3. 白话术语表

| 术语 | 白话 | 现场一句话 |
|------|------|------------|
| **FID** | Feature set ID，特性集标识 | 「这套信令挂在哪家门牌下」 |
| **SFID** | Standards FID，标准默认特性集 | 「ETSI 标准馆，门牌 0x00」 |
| **MFID** | Manufacturer's FID，厂商特性集 | 「品牌私密馆；没钥匙就别指望懂」 |
| **FLCO** | Full Link Control Opcode | 「Full LC 里的 6 bit 功能码」 |
| **CSBKO** | CSBK Opcode | 「控制信令块里的 6 bit 功能码」 |
| **Full LC** | 全链路控制 | 语音头/终止/嵌入里带地址与业务类型的那块 |
| **CSBK** | Control Signalling Block | 控制信令块（请求、应答、激活、前导等） |
| **FNS** | Feature Not Supported | 「你用标准门牌叫了一个我不支持的功能」 |
| **IOP** | Interoperability（产业认证语境） | 「协会测过的标准特性清单能否互通」 |
| **私有特性** | 规范未标准化、走 MFID 的能力 | 「增值功能，不承诺跨厂」 |

对照记忆（避免混）：

- **FID ≠ 地址**：地址是 24 bit 源/目的；FID 是特性集。  
- **FLCO ≠ CSBKO**：一个在 Full LC，一个在 CSBK；都是 6 bit，但表不同。  
- **SFID 下的 FLCO 数值** 与 **某 MFID 下的同数值** **不能**当成同一个功能。

## 4. 现场对照：谁会用到这一课

| 岗位 / 场景 | 你会碰到什么 | 本课怎么用 |
|-------------|--------------|------------|
| 协议/栈开发 | 实现组呼 LC、个呼 CSBK、Talker Alias | 标准路径固定写 **FID=0x00** + 表内 Opcode |
| 联调 / 互通测试 | A/B 厂组呼通、某「彩蛋功能」不通 | 先抓 **FID**；MFID 不通是预期，不是射频锅 |
| 产品 / 方案 | 「要不要把标准功能改成私有 Opcode」 | **不要**；规范禁止用 MFID「重包装」已标准化特性 |
| 测试 / 抓包 | 看 Voice LC Header / CSBK | 读 Octet0 的 Opcode、Octet1 的 FID |
| 售前 / 招投标 | 客户要「多厂家互通」 | 对齐 **标准特性 + IOP 证书范围**；私有特性单列 |
| 运维排障 | 「有时能通有时不能」 | 区分：射频/色码问题 vs FID/Opcode 不认 |

排障口诀：

1. 先确认频率、Colour Code、时隙、ID 是否匹配（L1/寻址）；  
2. 再看 Full LC/CSBK 的 **FID**；  
3. `0x00` → 查标准 Opcode 表；非 `0x00` → 问「是不是某厂私有特性」。

## 5. 外壳长什么样：Full LC 与 CSBK 里的门牌

引用资料库：`01-空中接口/CSBK与LC字段详表.md`、`02-语音业务/语音业务字段速览.md`。学习摘要，冲突以 ETSI 原文为准。

### 5.1 Full LC 外壳（语音头 / 终止 / 嵌入路径）

```text
Octet0:  PF(1) | Reserved(1) | FLCO(6)
Octet1:  FID(8)          ← 门牌在这里
Octet2–8: Full LC Data   ← 地址、Service Options 等（随 FLCO 变）
+ CRC（头/终止路径与嵌入路径长度不同，阶段 C 再拆）
```

标准语音业务公共前缀直觉：

> **PF=0，Reserved=0，FLCO=表内值，FID=`00000000`（SFID）。**

### 5.2 CSBK 外壳

```text
Octet0:  LB(1) | PF(1) | CSBKO(6)
Octet1:  FID(8)          ← 门牌同样在这里
Octet2–9: CSBK Data (64)
+ CRC-16
```

单块 CSBK 时 LB 通常为 `1`。标准控制信令同样默认 **FID=SFID**。

### 5.3 规范硬规则（请背下来）

来自 Part2 **clause 4.3 Feature interoperability**（精神一致，措辞以 PDF 为准）：

1. **FID** 标识特性集；**FLCO** 标识该集内的空中功能。  
2. 为确保空口互操作：**本文件已标准化且设备已提供的特性，只能通过默认 SFID + 对应 FLCO 访问**。  
3. **未**在本文件标准化的特性，只能通过 **MFID** 提供。  
4. 被**个呼**到却不支持某标准 Opcode 时，应使用 **FNS** 类信令礼貌拒绝（所有 MS 都应实现 FNS 相关能力；细节见 Part2）。

用大白话再说一遍：

> **标准功能不许偷偷换门牌；私有功能不许冒充标准门牌。**

## 6. SFID 下的功能码地图（与业务对照）

下面只列**标准馆（SFID）**里最常用的码，方便和第 13 课菜单对上。完整表见 `语音业务字段速览.md`。

### 6.1 常见 FLCO（Table B.1 学习摘要）

| FLCO | 别名 | 你在业务里认识它为 |
|------|------|-------------------|
| `000000` | Grp_V_Ch_Usr | 组呼（及全呼/广播等用组地址+Service Options 表达的形态） |
| `000011` | UU_V_Ch_Usr | 个呼语音信道用户 |
| `000100`…`000111` | Talker Alias 头/块 | 主叫别名（补充能力，嵌入超帧） |
| `001000` | GPS_Info | 嵌入 GPS 信息 |
| `110000` | TD_LC | **Part3** 数据终止 LC（别和语音 Terminator 混淆） |

### 6.2 常见 CSBKO（Table B.2 学习摘要）

| CSBKO | 别名 | 场景 |
|-------|------|------|
| `000100` | UU_V_Req | 个呼语音业务请求（OACSU 存在性检查） |
| `000101` | UU_Ans_Rsp | 个呼应答 |
| `100110` | NACK_Rsp | 否定应答（也可承载 FNS 等场景） |
| `111000` | BS_Dwn_Act | 唤醒/激活基站出站 |
| `111101` | Pre_CSBK | 前导（扫描/节电相关） |

### 6.3 和「业务种类」怎么叠

| 用户要的 | 空口门牌直觉 |
|----------|--------------|
| 标准组呼说话 | SFID + FLCO=`000000` + 组地址 |
| 标准个呼说话 | SFID + FLCO=`000011`；OACSU 时先 CSBKO=`000100/000101` |
| 标准主叫别名 | SFID + Talker Alias 系列 FLCO |
| 厂商「一键巡更语音」 | **MFID** + 厂商自定 Opcode（对端无该 MFID 则不通） |
| 标准短数据/PDP | Part3：标准化数据走规定头；非标准化走第二数据头里的 **MFID** 路径 |

Part3 提醒（本课不展开字段）：数据互操作同样有「标准路径 vs MFID」二分；标准化分组数据不得靠私有 FID「另起炉灶」来冒充标准。

## 7. 完整例子（请跟着走一遍）

### 例子 A · 标准组呼（应互通）

场景：台 A 向组 `000001` 发起组呼；台 B、C 同组。

1. 空口 Voice LC Header / 嵌入 LC：`FID=0x00`，`FLCO=000000`（Grp_V_Ch_Usr）。  
2. Service Options + Group address + Source address。  
3. 任意遵守 Part2 的他厂终端：认 SFID + 该 FLCO → 进组听。  
4. **结论**：这是 IOP 意义上「该通」的典型路径。

### 例子 B · 厂商私有特性（不通是预期）

场景：A 厂终端在语音中嵌入「私有导航提示 LC」。

1. 抓包见 `FID=0x10`（示例，落在 MFID 区；真实值以厂商申请为准），FLCO 某值。  
2. B 厂终端无此 MFID 解释逻辑 → **忽略**该 LC。  
3. 组呼语音本身若仍用 SFID+`000000`，语音可能仍通；**只有私有附加功能丢了**。  
4. **结论**：不要把「私有功能丢了」写成「DMR 不互通」；要写成「私有特性未纳入互操作范围」。

### 例子 C · 错误示范：标准个呼挂 MFID（破坏互操作）

场景：研发把 UU_V_Ch_Usr 改成 `FID=自家MFID`，FLCO 仍写 `000011`，「觉得更安全」。

1. 对端按规范只在 **SFID** 下认个呼 → 不认你的门牌。  
2. 联调失败；IOP 也过不了。  
3. **结论**：标准化特性**必须**留在 SFID；安全/差异化应走真正的私有特性或上层策略，而不是挪用标准 Opcode 换门牌。

### 例子 D · FNS（标准门牌，但不支持该功能）

场景：台 A 用 SFID + 某标准 CSBKO 个呼台 B；B 未实现该可选标准特性。

1. B 识别门牌是 SFID，但 Opcode 自己不做。  
2. B 回 FNS / 相关 NACK 类信令（礼貌拒绝）。  
3. **结论**：这是「标准馆里缺货」，不是「进错商场」。排障应查能力清单/选配，而不是先拧天线。

### 例子 E · 射频伪装成互操作故障（对照弱项）

场景：FID/FLCO 全对，但场强极差、误码高。

1. 终端表现：时通时断、头 LC 解不出 → 有人误判「厂家不互通」。  
2. 真因可能在 L1：频率偏移、天线、干扰、越区。  
3. **结论**：互操作课也要会分流——**先证明比特稳定，再吵门牌**。频谱直觉见加餐文。

## 8. 对照表：你会在哪些 PDU 里看见 FID

把「门牌」钉到具体 PDU，避免只会背名词。

| PDU / 路径 | Opcode 字段名 | FID 在哪 | 典型用途 |
|------------|---------------|----------|----------|
| Voice LC Header | FLCO | Octet1 | 语音开始：组呼/个呼用户 LC |
| Terminator with LC | FLCO | Octet1 | 语音结束；常与通话中同一 Voice Channel User LC |
| 嵌入 LC（超帧 B–F） | FLCO | Octet1 | 迟后进入可读地址；Talker Alias / GPS 等 |
| CSBK | CSBKO | Octet1 | 个呼请求/应答、BS 激活、前导、NACK/FNS 等 |
| Short LC（经 CACH） | SLCO | （Short LC 结构不同，本课不展开） | 活动更新等；互操作主矛盾仍在 Full LC/CSBK |
| Part3 数据头 | （数据格式字段） | 非标准化时第二数据头带 MFID | 标准 PDP vs 厂商数据 |

现场抓包顺序建议：

1. 先认 Data Type（这是 Voice LC Header？CSBK？Terminator？）。  
2. 读 Octet0 低 6 bit → FLCO 或 CSBKO。  
3. 读 Octet1 → FID。  
4. `FID==0`：查 Part2 Annex B；否则查厂商文档/MFID 表。  
5. 再解后面的地址与 Service Options。

## 9. 和服务选项、补充业务怎么分工（防混淆）

第 13 课讲过 **Service Options（8 bit）**：紧急、广播、优先级、OVCM、双时隙等「加料」。本课的 FID/FLCO 是另一轴线：

| 轴线 | 回答的问题 | 典型字段 |
|------|------------|----------|
| 特性集互操作 | 「这是哪一套字典里的哪一个词？」 | FID + FLCO/CSBKO |
| 补充业务加料 | 「这次标准呼叫要不要加急/广播/…？」 | Service Options 等 |
| 寻址 | 「谁跟谁说？」 | 24 bit Source / Dest 或 Group |

三者同时正确，一次标准组呼才「又认得、又找对人、又加对料」：

```text
FID=SFID  +  FLCO=Grp_V_Ch_Usr  +  Group ID 对  +  Service Options（如 Emergency）
```

私有特性往往**自己重定义**整段 LC 数据含义，不能假设 Service Options 比特还按 Table 7.11 解释。

## 10. 排障剧本（把课用到明天的工单）

### 剧本 1 ·「两家手台组呼正常，一键告警对面没反应」

1. 确认告警是标准 Emergency（Service Options）还是厂商「一键告警应用」。  
2. 抓空口：若告警 PDU 的 FID≠0x00 → 按 MFID 特性排查，换他厂机本来就不该通。  
3. 若 FID=0x00 且 FLCO/CSBKO 为标准紧急相关路径 → 查对端是否实现该**可选**标准特性、是否回 FNS。

### 剧本 2 ·「写着 DMR 的车载台，个呼 OACSU 无应答」

1. 查是否发出 UU_V_Req（CSBKO=`000100`）且 FID=SFID。  
2. 对端是否实现 OACSU（有的部署只用 PATCS 直接讲）。  
3. 若对端回 NACK/FNS → 读原因；若完全无 CSBK → 查信道/时隙/色码/礼貌接入，先排除 L1。

### 剧本 3 ·「升级固件后，他厂中继不认我们的某某功能」

1. 列出该功能是标准还是私有。  
2. 私有：查 MFID 是否变更、对端是否曾特制支持旧 MFID。  
3. 标准：查是否误把 FID 改非零（回归缺陷）；IOP 证书是否绑旧软件版本。

### 剧本 4 ·「仪表能解语音，却解不出别名」

1. Talker Alias 是 SFID 下 FLCO `000100`–`000111` 的嵌入 LC。  
2. 若发送端用私有格式塞「名字」→ 标准仪表/他厂机只认标准 Alias FLCO。  
3. 别把「没有别名」说成「组呼失败」——组呼 LC 与 Alias LC 是不同 FLCO。

## 11. 产业侧：IOP 认证在测什么（建立语感）

DMR Association 维护自愿的 **IOP（互操作）认证**流程：针对 Tier II / Tier III 的**强制与可选标准特性**做厂间对测，并保存空口日志。证书按硬件平台与软件版本管理。

对你有用的三句话：

1. **IOP 测的是标准特性清单**，不是某厂全部私有功能。  
2. 招投标写「多厂家互通」时，应对齐证书上的 **强制项**（如组呼、个呼 PATCS/OACSU、全呼等——以协会现行清单为准）。  
3. 私有特性可以卖点很亮，但要在方案书里**单独标注「仅本厂/本 MFID」**。

再补两条现场常用判断：

4. 证书通常**绑定硬件平台 + 软件版本**；大版本升级后旧证书不能想当然沿用。  
5. 「可选特性」即便是标准的，对端也可以不做；此时更常见的是能力不齐或 FNS，而不是「DMR 假冒」。

详细流程与清单见本课「推荐阅读」中的协会材料。

## 12. 常见误区

1. **「都是 DMR，一定互通」**  
   错。互通的是 **SFID 下的标准特性**；MFID 私有不保证。

2. **「FID 就是设备 ID / 电台号」**  
   错。电台号是 24 bit 地址；FID 是 8 bit 特性集门牌。

3. **「FLCO 和 CSBKO 是同一个表」**  
   错。都是 6 bit，但分属 Full LC 与 CSBK，枚举不同。

4. **「把标准组呼改成 MFID 更有利于绑定客户」**  
   错，且违规于互操作设计：标准化特性必须经 SFID 暴露。

5. **「对端忽略我的私有 LC，就是协议栈有 Bug」**  
   通常不是。无对应 MFID 时忽略是正常行为。

6. **「FNS 等于呼叫失败因为信道忙」**  
   不必然。FNS 更接近「功能不支持」；忙/拒绝还有其他 Reason/NACK 语义（集群侧更复杂，后课再讲）。

7. **「Colour Code 不同也能靠 SFID 互通」**  
   Colour Code 管同频系统区分；门牌对了但色码不对，照样不该进错系统。两者都要满足。

8. **「Part3 数据没有互操作问题」**  
   有。标准化数据走规定头；非标准化走 MFID 路径。别用私有头冒充标准 PDP。

## 13. 自测（4–6 题）

**题 1.** SFID 的典型取值是什么？它代表什么？  
<details><summary>参考答案</summary>
`00000000`（0x00）。表示 TS 102 361-2 的标准默认特性集（Standards Feature ID）。
</details>

**题 2.** 规范要求：设备已实现的、Part2 已标准化的特性，应如何在空口上暴露？  
<details><summary>参考答案</summary>
只能通过 **默认 SFID + 对应的标准 FLCO（或同类标准 Opcode）** 访问；不得改挂 MFID 来「重包装」标准特性。
</details>

**题 3.** 抓包见 Full LC：`FID=0x00`，`FLCO=000011`。这最可能是什么业务？  
<details><summary>参考答案</summary>
标准个呼语音信道用户 LC（UU_V_Ch_Usr）。
</details>

**题 4.** A 厂私有巡更功能，B 厂终端完全无反应，但标准组呼正常。最可能的原因？  
<details><summary>参考答案</summary>
巡更走 **MFID**，B 厂无该特性集；组呼走 SFID 故仍通。属于预期的私有特性不互通，不是「DMR 坏了」。
</details>

**题 5.** FID 落在 `00000100`…`01111111` 区间意味着什么？  
<details><summary>参考答案</summary>
**MFID 厂商区**（学习摘要）。应按厂商特性集解释；他厂设备通常不保证理解。
</details>

**题 6.** 什么是 FNS？它和「进错 MFID 商场」有何不同？  
<details><summary>参考答案</summary>
FNS = Feature Not Supported：门牌仍是 **SFID**，但该标准 Opcode 本机未实现，礼貌拒绝。  
「进错 MFID」则是对端根本不在你的私有门牌体系里，往往直接忽略，而不是按标准 FNS 语义应答。
</details>

## 14. 本节钉死的句子（可直接对外讲）

1. **FID 是特性集门牌；FLCO/CSBKO 是门牌下的功能码。**  
2. **SFID=0x00 是标准馆；标准业务必须开在标准馆。**  
3. **MFID 是厂商私密馆；不通往往是预期，不是天线锅。**  
4. **禁止把已标准化特性改挂 MFID；禁止用 SFID 冒充私有语义。**  
5. **同频、同色码、同地址只保证「能听见比特」；FID+Opcode 一致才谈得上「听懂业务」。**  
6. **IOP 认证对齐的是标准特性清单；私有特性要在方案里单列。**  
7. **Service Options 是加料，FID/FLCO 是词典；两者都对才算一次标准呼叫完整。**  
8. **排障先分流：L1 不稳先修射频；门牌不对再吵厂家。**
