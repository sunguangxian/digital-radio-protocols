> **频谱 / 调制提醒（一小段，不是本篇主线）**：RF 仍是整条 **12.5 kHz**；调制仍是 **4FSK**（约 **4800 baud → 9.6 kbps** 毛速率）；空口仍是 **2-slot TDMA**，时隙 **30 ms**。Stun / Revive / Kill、短信、DGNA **默认都在控制信道（TSCC）上完成**，不另占业务信道——这是容量规划口吻，不是「调制坏了」。频率/带宽/调制四句话见 `学习推送/加餐_频率带宽与调制解调.md`；本篇主线是 **运维分诊 + 投诉标准回复话术**。

## 1. 为什么要写这篇手册（动机 + 现场对话）

第 39 课已经把协议钉子钉牢：网关名片、C_AHOY Flag、UDT 长度、DGNA 15+1。第 40 课运维 Week‑2 只要你交付一样东西：

> **一页「投诉话术」：个呼 / 组呼 / Stun 预期。**

手册 01 专治「登不上」；手册 02 专治「Grant 了没声」；本篇专治另一类更高频的**管理类与短数据类**投诉——协议你会背，值班却卡在嘴上：

> 「用户说禁了还有定位点，是不是没禁上？」  
> 「网管显示短信已送达，对方说没收到，谁撒谎？」  
> 「调度临时加了个抢险组，巡逻组怎么没了？」

现场你一定听过这些对话：

- 调度：「手台丢了，网管说已经远程禁用了，地图上还能看见它在移动！」——你若答「那可能没禁上」，就把 **Stun 的设计当成了故障**（第 39 课：Stun 保留猎站/登记/鉴权/定位）。  
- 用户：「短信显示已送达，对方说根本没弹窗。」——你若立刻查射频，可能漏问第一句：**个呼还是组呼？** 组呼回的是网络侧 **Message_Accepted**，不是「某人已读」。  
- 班长：「我给 20 台加了『抢险 1 组』，原来的『巡逻 3 组』全没了！」——**DGNA Address 模式是整表替换**；漏带旧组 = 人为「组丢了」，不是空口随机丢包。  
- 网管新人：「点了永久禁用，网管一直转圈，要不要连点三次？」——Kill 必须鉴权；终 ACK 丢失时，重复硬点可能掩盖「可能已生效」；先核钥匙与空口，不盲着重发（第 39 课口径）。  
- 投诉坐席：「用户骂我们『已送达还没到』。」——若工单没写「个呼/组呼」栏，话术卡无法开口。  
- 测试：「Stun 之后手台还在登记，是不是 Stun 失败了？」——**登记还在，恰恰说明 Stun 路径可能是对的**；成败标准是**用户业务是否已停**。  
- 调度台：「Alias 模式发了一个带名字的组，为什么 Address 列表里那 15 个没变？」——**Address 与 Alias 预期不同**；别用 Address 话术回 Alias 单。

培训台如果只背「网管有禁用、恢复、永久禁用、动态组、短信五个按钮」，值班会卡在同一处：

> **会背按钮名 ≠ 会回投诉。**  
> 分诊 = 每次工单强制**先分三线**：  
> **① Stun 线**：Stun vs Revive vs Kill 效果表；成败 = 业务是否已停/恢复（不是地图有无点）。  
> **② 短信线**：先问个呼还是组呼；个呼看 ACK 镜像，组呼「已送达」≠某人已读。  
> **③ DGNA 线**：Address 整表替换；15+1；Alias vs Address 预期。  
> 三线各有**标准回复话术**；答不清，不许升级为「射频坏了」或「用户撒谎」。

本篇目标：能画出三线投诉总图；会用效果表解释 Stun/Revive/Kill；会把短信投诉第一句问成「个呼还是组呼」；会解释 DGNA「组丢了」多半是漏带旧组；能填完《本网 Stun·DGNA·短信投诉话术卡》；自测过关后，回库翻第 39/40 课与 `Stun_DGNA_UDT与定时器.md` 把本网话术补进卡片——**不重做第 39 课手拼作业**。

**本篇硬禁令（写进脑子）**：Stun / Revive / Kill **只允许网络管理口径**——远程禁用 / 恢复 / 永久禁用；**不写攻击面、不写如何绕过、不写恶意利用步骤**；不发明 ETSI 条款号（入口锚点以资料库 `04-集群协议/Stun_DGNA_UDT与定时器.md`、第 39/40 课、手册 01/02 已有编号为准）；**不重 dump MSC / FEC / Grant 地图 / Reason 全表**；不重手拼第 39 课全部字节例（本篇只留网关 ID 与成败语义）；不把厂商中文提示当成 ETSI 正式名；**不写真实批复频点 / 站点号 / 真实用户个号进公开仓库**；本篇不写下一篇手册正文。

## 2. 总图 / 故事：同一套前台，三条投诉线

### 2.1 一句话：三线都在「旅馆前台」，但成败标准完全不同

继续旅馆比喻（第 31–40 课 + 手册 01/02）：

| 旅馆 | 空口 | 本篇投诉常卡在哪 |
|------|------|------------------|
| 前台 | **TSCC** | 三线默认都在前台办，不进客房 |
| 前台发「暂停房卡权限」 | **Stun**（STUNI） | 人还在酒店里走动（登记/定位），却不能点餐——用户以为「没禁上」 |
| 前台发「恢复房卡权限」 | **Revive**（仍从 STUNI） | 业务应恢复；若未恢复才查空口 ACK |
| 前台发「永久销户」 | **Kill**（KILLI） | 不可空口 Revive；必须鉴权；终 ACK 丢了≠一定没生效 |
| 前台传纸条 | **短信 / UDT**（SDMI） | 个呼有回执镜像；组呼只保证「前台已广播」，不保证每人读到 |
| 前台发「今日临时工作牌清单」 | **DGNA**（DGNAI） | Address 模式 = **整表换牌**；漏写旧牌 → 「牌丢了」投诉 |

口诀：**先分线 → 再对成败标准 → 再开口回用户。**  
把「Stun 后地图还有点」写成故障，或把「组短信已送达」写成「对方已读」，是本篇最常见的两大口误。

### 2.3 对照图：三条「像故障其实是预期」

```text
  A. Stun 后地图还有点（常被误判）
     网管 Stun 成功 → 用户业务已停
     但猎站/登记/鉴权/定位仍可用
     ※ 「还有点」= 设计；「还能个呼/组呼/短信」才是失败

  B. 组短信「已送达」对方说没收到（常被误判）
     网络回 Message_Accepted（学习口径：网络已接受/已发给组）
     ※ 不是「某台手台已读」；先问个呼还是组呼

  C. DGNA 后旧动态组失踪（常被误判为「空口丢了」）
     Address 模式成功 → 整表替换 ADDRESS1…15
     ※ 新清单没带旧组 = 人为删除；要追加必须旧组一起再发
```

对照口诀：

| 你想确认的事 | 成功长什么样 | 失败 / 假故障长什么样 |
|--------------|--------------|------------------------|
| **Stun 办成了吗？** | 用户业务已停；登记/定位仍可 | 仍能个呼/组呼/短信 → 查空口 ACK / 是否未支持 |
| **Revive 办成了吗？** | 用户业务恢复 | 仍停业务 → 查是否真 Revive、空口是否成功 |
| **Kill 办成了吗？** | 全部 DMR 功能永久失去；空口不能 Revive | 鉴权失败则状态不变；无终 ACK 时可能已生效 |
| **个呼短信到了吗？** | 被叫 ACK + 镜像给主叫 | 无镜像 / NACK → 按信令排 |
| **组短信「到了」吗？** | 网络 Message_Accepted | **不等于**组员已读；覆盖/正忙于业务信道等 |
| **DGNA 加组办成了吗？** | 清单与预期一致（含旧组） | 漏带旧组 → 「组丢了」投诉 |

## 3. 三线分诊 + 「投诉三联单」

### 3.1 三线工作流（每次工单照念）

把下面三块贴在网管 / 投诉坐席屏边上（第 40 课 Week‑2 加厚）：

```text
① Stun 线（远程禁用 / 恢复 / 永久禁用）
   → 先确认操作意图：Stun？Revive？Kill？（网络管理口径）
   → 网关名片：STUNI=`FFFECC`（Stun/Revive）；KILLI=`FFFECF`（Kill）
   → 成败标准：**用户业务是否已停 / 已恢复**（个呼、组呼、短信、数据）
   → 「地图上还有没有点」「还在不在登记」**不是** Stun 失败证据——它们常被保留
   → Kill：永久；空口不能 Revive；必须鉴权；终 ACK 丢失时先核是否已生效
   → 不支持：常见空口口径 C_NACKU + MSNot_Supported（学习记 `0x00`）——与信号无关

② 短信线（短数据 / UDT）
   → **第一句：个呼还是组呼？**
   → 网关名片：SDMI=`FFFEC5`（TSCC 以它的名义「要货」）
   → 个呼：被叫应 ACK；主叫侧常见为镜像 Reason（学习口径：对方收妥才算「真到了」）
   → 组呼：网络 Message_Accepted（学习记 `0x60`）=「网络已发给这个组」
        **≠「某一台已读」**；组成员不回确认
   → UDT 长度教学点：头 + 1…4 附块 → 约 **80 / 176 / 272 / 368 bit**（变长二进制上限记法见第39课；本篇不手拼）
   → 过长 / 编码不符：先查长度与格式，再查射频

③ DGNA 线（动态组）
   → 网关名片：DGNAI=`FFFED6`
   → Address 模式：最多 15 个 24-bit 组号；**成功则整表替换**原 ADDRESS1…15
   → 漏带旧组 → 典型投诉「组丢了」——先查下发清单，别先骂空口
   → Alias 模式：再加 1 个带别名的组位（15+1=16）；预期与 Address 不同
   → 清空 / 删除：空位 ADRNULL 等写法回第39课 / 笔记；本篇话术强调「写清意图再下发」
```

**结束条件**：三线之一已选定 + 成败标准已对用户说清 + 空口/网管证据（脱敏）写入话术卡，才能谈「换机 / 重发 / 升级射频」。只有中文「禁了没反应 / 已送达没收到 / 组没了」= 线索不足。

### 3.2 决策树（口述版）

```text
工单：Stun异常 / 短信纠纷 / DGNA组丢了 / 「禁了还有点」
        │
        ▼
  主题分流：Stun？短信？DGNA？（可多线，但每次先钉一条主线）
        │
   Stun ──► 意图=Stun/Revive/Kill？
        │     业务已停/恢复？──是──► 用「预期说明」话术结案（地图有点=正常）
        │                    ──否──► 查空口 AHOY/ACK；MSNot_Supported？鉴权失败？
        │
   短信 ──► 个呼还是组呼？
        │     个呼：有无被叫ACK/镜像？──无──► 信令排障（可达/拒绝/超时）
        │     组呼：Message_Accepted？──是──► 「已送达≠已读」话术；查对方是否在控/覆盖
        │
   DGNA ──► Address 还是 Alias？
              Address：下发清单是否含全部应保留旧组？──否──► 「整表替换」说明+重发完整表
              Alias：是否误用 Address 预期检查？──是──► 换预期再查
```

## 4. 深挖三线（运维语义，不是第 39 课重播）

### 4.1 Stun 线：效果表（必背）

只记效果与恢复关系；过程场回第 39 课 / `Stun_DGNA_UDT与定时器.md` §1。

| 动作 | 白话（网络管理） | 用户业务 | 仍可用（典型） | 空口恢复 |
|------|------------------|----------|----------------|----------|
| **Stun** | 远程禁用（暂时） | 停：不得请求/接收该网上用户发起的业务 | 猎站、登记、鉴权、Stun/Revive、**定位** | **Revive**（仍从 STUNI） |
| **Revive** | 远程恢复 | 恢复 | — | — |
| **Kill** | 永久禁用 | **永久**失去全部 DMR 功能 | 无 | **任何空口消息都不能 Revive** |

网关（学习记法）：

| 业务 | Gateway | ID |
|------|---------|-----|
| Stun / Revive | **STUNI** | `FFFECC` |
| Kill | **KILLI** | `FFFECF` |

**成败标准（钉死）**：

1. Stun 成功 = **用户业务已停**（个呼/组呼/短信/数据发不出也收不到）。  
2. 「地图还有点 / 还在登记」= **常见预期**，不是失败证据。  
3. Revive 成功 = **用户业务恢复**。  
4. Kill 成功 = 功能永久失去；失败常见先看**反向鉴权 / 钥匙**；无最终 ACK 时考虑「可能已生效、ACK 丢失」（第 39 课）。  
5. 终端回「不支持」类 NACK（学习记 MSNot_Supported）= 能力问题，不是覆盖问题。

**权限提醒（一句话）**：谁能点 Stun/Kill、如何审计，属于**运营制度**，不在空口标准里；本篇只教你如何解释空口预期与如何回话。

### 4.2 短信线：个呼 ACK 镜像 vs 组呼 Message_Accepted

| 项 | 个呼短信 | 组呼短信 |
|----|----------|----------|
| 第一问 | 确认是个呼 | 确认是组呼 |
| 网络侧常见成功语义 | 被叫收妥后 ACK；主叫侧见**镜像** | **Message_Accepted**：网络已发给该组 |
| 用户口语「已送达」 | 较接近「对方终端已确认」 | **只保证网络发出，不保证某人已读** |
| 排障第一刀 | 查被叫 ACK / 镜像 / NACK | 说明语义；再查对方是否在控、覆盖、是否正忙于业务信道 |

SDMI = `FFFEC5`（短数据服务名片）。  
UDT 长度（教学点到即可）：头 + 1…4 附块 → **80 / 176 / 272 / 368 bit** 四级容量直觉；超长先砍字数/换格式，再查空口。细节与「收到」手拼回第 39 课。

### 4.3 DGNA 线：整表替换与 15+1

| 模式 | 容量直觉 | 成功后手台行为 | 投诉高发点 |
|------|----------|----------------|------------|
| **Address** | 最多 **15** 个动态组号 | **删除**原 ADDRESS1…15，写入新清单（空位 ADRNULL） | 漏带旧组 → 「组丢了」 |
| **Alias** | 再 **+1** 个带别名的组位 | 与 Address 列表预期不同；可给组挂名 | 用 Address 话术检查 Alias 单 |

DGNAI = `FFFED6`。  
口诀：**要追加，必须把旧组一起再写进新表。**  
调度下发前强制核对：「完整清单 = 旧保留组 ∪ 新组」。

### 4.4 四张名片速记（只留本篇要用的）

| ID | Alias | 本篇用途 |
|----|-------|----------|
| `FFFECC` | STUNI | Stun / Revive |
| `FFFECF` | KILLI | Kill（永久禁用） |
| `FFFED6` | DGNAI | 动态组 |
| `FFFEC5` | SDMI | 短数据 / 短信要货 |

补充业务大类 Service_Kind = `1101`（Stun/Kill/DGNA 等）；短信短数据常用 `0100`/`0101` 家族——细节回第 39 课，本篇以名片 + 成败标准为主。

### 4.5 和手册 01 / 02 的「接口贴纸」

```text
  登记失败？ ──────────► 手册01 三问（本篇 Stun 后「仍登记」不要误跳）
  Grant了没声？ ────────► 手册02 四问（本篇不抢射频优先）
  禁了还有点 / 短信纠纷 / 组丢了？ ► 本篇三线 + 话术卡
```

三张贴纸并排：症状分流，不抢剧本。

### 4.6 「先语义后射频」反例集

| 反例 | 错在哪 | 正解 |
|------|--------|------|
| Stun 后见定位点 → 判失败 | 把设计当故障 | 查用户业务是否已停 |
| 组短信已送达 → 承诺「他已读」 | 语义升级 | Message_Accepted ≠ 已读 |
| DGNA 后旧组没了 → 查射频 | 根因常是清单 | 先对完整表 |
| Kill 无 ACK → 连点 | 可能已生效 | 先核鉴权与状态 |
| 短信失败 → 先换天线 | 可能超长/组呼语义 | 先分个组呼与长度 |

## 5. 现场映射：标准回复话术（可直接照着说）

### 5.1 Stun 线 · 投诉标准回复

**对话 S1 · 「禁了为什么地图还有点？」**

> 远程禁用（Stun）的设计就是：暂停这台终端在本网上的**用户业务**（通话、短信等），但仍然允许它**猎站、登记，并继续提供定位**，方便找回设备。  
> 所以「地图上还有点」通常**不代表没禁上**。我们以「是否还能打电话/发短信」为成败标准。  
> 我这边核一下：业务是否已停？空口是否收到成功确认？……

**对话 S2 · 「说禁了还能打电话」**

> 那就按失败或未生效处理：我查远程禁用命令是否发出、终端回的是成功确认还是「不支持」、是否其实点成了别的操作。  
> 请先不要反复猛点；我们先看空口证据。

**对话 S3 · 「恢复了还是不能用」**

> 恢复（Revive）成功的标准是用户业务回来。我核：是否确实发的是恢复而不是再次禁用、空口确认是否成功、终端是否处于永久禁用（Kill）状态——永久禁用**不能**靠空口恢复。

**对话 S4 · 「永久禁用一直转圈」**

> 永久禁用必须先通过终端对网络的鉴权。转圈时我先查鉴权是否失败、钥匙配置是否一致，以及是否已经生效但最终确认丢失。  
> 不建议连续硬点；需要按授权流程处理。

### 5.2 短信线 · 投诉标准回复

**对话 M1 · 接单第一句（强制）**

> 请问这条短信是发给**一个人**，还是发给**一个组**？

**对话 M2 · 个呼「已送达对方说没收到」**

> 个呼短信在机制上更接近「对方终端确认收妥后，网络再镜像给发送方」。  
> 若发送方看到成功、对方坚称没有，我们查：被叫确认/镜像是否完整、对方当时是否在服务区、终端是否过滤/存储异常。  
> 请提供发送时间与双方号（内部工单填，**公开材料勿写真实号**）。

**对话 M3 · 组呼「已送达对方说没收到」**

> 组短信的「已送达」在标准语义里，通常表示**网络已经把这条消息发给该组**，**不等于组里每一个人、某一台指定手台已经读到**。  
> 对方当时若不在覆盖、正占用业务信道、或未守在控制信道，都可能收不到，而这**不一定是发送失败**。  
> 若业务上必须确认到人，应改用**个呼短信**或语音点名流程，而不是把组短信当已读回执承诺用户。

**对话 M4 · 「短信太长发不出去」**

> 控制信道短数据有长度台阶（学习记 80/176/272/368 bit 四级直觉）。请先缩短内容或分段；我再帮看是否格式/编码不匹配。

### 5.3 DGNA 线 · 投诉 / 调度标准回复

**对话 D1 · 「临时加组，旧组没了」**

> 动态组的 **Address 模式是整表替换**：新清单成功写入后，手台会先清掉原来的动态组表，再写入新表。  
> 如果下发时只写了新组、没把需要保留的旧组一起带上，旧组就会「消失」——这通常是清单问题，不是射频随机丢组。  
> 处理：用**完整清单**（旧保留组 + 新组）再发一次。

**对话 D2 · 调度下发前确认（主动话术）**

> 下发前请确认：这是 Address 整表，还是 Alias 挂名？  
> Address 的完整清单是否包含所有要保留的旧动态组？最多 15 个号位；再加带名的那 1 个走 Alias 预期。

**对话 D3 · 「组名不对 / 只有名字没有号」**

> 先确认走的是 Alias 还是 Address。两种模式预期不同，不能混用同一套检查表。

## 6. 工作实例（厚例 · 教学虚构）

> 示例网号口径沿用第 38/39 课教学网 **NP=401**；号码与站点均为**虚构**，勿对照真实批复。

### 例 1 · Stun 后「地图还有点」——把设计当故障

**现象**：调度投诉「手台 40125312 已远程禁用，地图仍移动」。  
**分诊**：Stun 线。查用户业务——个呼/组呼已不可用；登记与定位仍在。  
**结论**：Stun **成功**；「还有点」为预期。  
**回复**：用对话 S1；工单结案写「业务已停；定位保留属设计」。  
**反例**：若业务仍可打通，才升为「未生效/不支持/命令未到」。

### 例 2 · 组短信「已送达」三人没收到

**现象**：班长向组 40125934 发通知，网管显示已送达；三名组员说没弹窗。  
**分诊**：短信线 → **组呼**。  
**结论**：Message_Accepted 只说明网络已发给组；需逐人核覆盖/是否在控/是否业务信道占用；**不能**对用户承诺「组短信=全员已读」。  
**回复**：对话 M3；建议关键通知改个呼或语音点名。

### 例 3 · DGNA 漏带旧组 → 「巡逻组丢了」

**现象**：抢险日给 20 台写入新组「抢险1」；次日投诉「巡逻3」没了。  
**分诊**：DGNA Address。核对下发清单：只有新组，未带旧组。  
**结论**：整表替换的人为结果。  
**处理**：完整表重发（旧∪新）；对话 D1；更新调度检查单（对话 D2）。

### 例 4 ·（加分）Kill 终 ACK 丢失

**现象**：永久禁用后网管超时；终端已无任何响应。  
**分诊**：按第 39 课——可能已生效；再发可能收不到响应。  
**动作**：先核鉴权历史与终端状态；**不**在未授权情况下反复硬点；升级按运营制度。

### 例 5 ·（干净对照）个呼短信成功

**现象**：40125312 → 40125313 发「收到」；双方确认弹窗一致。  
**分诊**：个呼；存在被叫确认与主叫侧镜像成功语义。  
**用途**：给新人当「真已送达」对照样板，对比例 2。

### 例 6 · Stun「不支持」

**现象**：网管提示终端不支持远程禁用。  
**分诊**：空口常见 MSNot_Supported；与信号无关。  
**回复**：说明机型/特性未实现；改走运营授权的其他处置流程（制度侧，不写攻击替代方案）。

### 例 7 · Alias 与 Address 预期混单

**现象**：只下发了带别名的一组，坐席却用「15 个 Address 列表」验收，报失败。  
**分诊**：先分模式；Alias 成功不等于 Address 表应出现 15 行。  
**回复**：对话 D3。

### 例 8 · 短信超长

**现象**：长通知发不出。  
**分诊**：先长度台阶（80/176/272/368 bit 直觉），再空口。  
**处理**：分段；对话 M4。

8. **整表替换**删除旧 ADDRESS1…15；追加时旧组必须写进新清单。  
9. 15 个 Address + 1 个 Alias 位；模式不同预期不同。  
10. **80 / 176 / 272 / 368 bit**；先缩短/分段。  
11. 可能已生效；再发可能无响应；先核鉴权与状态，按授权处理。  
12. 登记→01，Grant无声→02，Stun/短信/DGNA→03；Stun 后仍登记**通常不应**当登记失败单。

## 11.7 常见问法速查（FAQ 式）

**Q1：Stun 后还在登记，要不要开手册 01？**  
A：一般不要。仍登记常是 Stun 预期；先核用户业务是否已停。

**Q2：组短信能否当考勤「已读」？**  
A：**不能**按标准语义承诺。要到人用个呼或语音流程。

**Q3：Revive 能救回 Kill 吗？**  
A：**不能**靠空口 Revive。Kill 是永久禁用口径。

**Q4：DGNA 能不能「只追加一个组」？**  
A：Address 模式语义是整表替换；追加必须带上旧组再发完整表。

**Q5：话术卡能否写真实用户号方便夜班？**  
A：**不能写进学习推送/公开仓。** 真实号只留在受控工单系统。

**Q6：本篇要不要会手拼 C_AHOY 字节？**  
A：值班话术**不要求**重做第 39 课手拼；会认名片与 ACK 语义即可。要深挖再回第 39 课。
