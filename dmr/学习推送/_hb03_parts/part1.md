> **频谱 / 调制提醒（一小段，不是本篇主线）**：RF 仍是整条 **12.5 kHz**；调制仍是 **4FSK**（约 **4800 baud → 9.6 kbps** 毛速率）；空口仍是 **2-slot TDMA**，时隙 **30 ms**。Stun / Revive / Kill、短信、DGNA **默认都在控制信道（TSCC）上完成**，不另占业务信道——这是容量规划口吻，不是「调制坏了」。频率/带宽/调制四句话见 `学习推送/加餐_频率带宽与调制解调.md`；本篇主线是 **运维分诊 + 投诉标准回复话术**。

## 1. 为什么要写这篇手册（动机 + 现场对话）

第 39 课已经把协议钉子钉牢：网关名片、C_AHOY Flag、UDT 长度、DGNA 15+1。第 40 课运维 Week‑2 只要你交付一样东西：

> **一页「投诉话术」：个呼 / 组呼 / Stun 预期。**

手册 01 专治「登不上」；手册 02 专治「Grant 了没声」；本篇专治另一类更高频的**管理类与短数据类**投诉——协议你会背，值班却卡在嘴上：

> 「用户说禁了还有定位点，是不是没禁上？」  
> 「网管显示短信已送达，对方说没收到，谁撒谎？」  
> 「调度临时加了个抢险组，巡逻组怎么没了？」

现场你一定听过这些对话：

- 调度：「手台丢了，网管说已经远程禁用了，地图上还能看见它在移动！」——你若答「那可能没禁上」，就把 **Stun 的设计当成了故障**（第 39 课：Stun 保留猎站/登记/鉴权/定位）。  
- 用户：「短信显示已送达，对方说根本没弹窗。」——你若立刻查射频，可能漏问第一句：**个呼还是组呼？** 组呼回的是网络侧 **Message_Accepted**，不是「某人已读」。  
- 班长：「我给 20 台加了『抢险 1 组』，原来的『巡逻 3 组』全没了！」——**DGNA Address 模式是整表替换**；漏带旧组 = 人为「组丢了」，不是空口随机丢包。  
- 网管新人：「点了永久禁用，网管一直转圈，要不要连点三次？」——Kill 必须鉴权；终 ACK 丢失时，重复硬点可能掩盖「可能已生效」；先核钥匙与空口，不盲着重发（第 39 课口径）。  
- 投诉坐席：「用户骂我们『已送达还没到』。」——若工单没写「个呼/组呼」栏，话术卡无法开口。  
- 测试：「Stun 之后手台还在登记，是不是 Stun 失败了？」——**登记还在，恰恰说明 Stun 路径可能是对的**；成败标准是**用户业务是否已停**。  
- 调度台：「Alias 模式发了一个带名字的组，为什么 Address 列表里那 15 个没变？」——**Address 与 Alias 预期不同**；别用 Address 话术回 Alias 单。

培训台如果只背「网管有禁用、恢复、永久禁用、动态组、短信五个按钮」，值班会卡在同一处：

> **会背按钮名 ≠ 会回投诉。**  
> 分诊 = 每次工单强制**先分三线**：  
> **① Stun 线**：Stun vs Revive vs Kill 效果表；成败 = 业务是否已停/恢复（不是地图有无点）。  
> **② 短信线**：先问个呼还是组呼；个呼看 ACK 镜像，组呼「已送达」≠某人已读。  
> **③ DGNA 线**：Address 整表替换；15+1；Alias vs Address 预期。  
> 三线各有**标准回复话术**；答不清，不许升级为「射频坏了」或「用户撒谎」。

本篇目标：能画出三线投诉总图；会用效果表解释 Stun/Revive/Kill；会把短信投诉第一句问成「个呼还是组呼」；会解释 DGNA「组丢了」多半是漏带旧组；能填完《本网 Stun·DGNA·短信投诉话术卡》；自测过关后，回库翻第 39/40 课与 `Stun_DGNA_UDT与定时器.md` 把本网话术补进卡片——**不重做第 39 课手拼作业**。

**本篇硬禁令（写进脑子）**：Stun / Revive / Kill **只允许网络管理口径**——远程禁用 / 恢复 / 永久禁用；**不写攻击面、不写如何绕过、不写恶意利用步骤**；不发明 ETSI 条款号（入口锚点以资料库 `04-集群协议/Stun_DGNA_UDT与定时器.md`、第 39/40 课、手册 01/02 已有编号为准）；**不重 dump MSC / FEC / Grant 地图 / Reason 全表**；不重手拼第 39 课全部字节例（本篇只留网关 ID 与成败语义）；不把厂商中文提示当成 ETSI 正式名；**不写真实批复频点 / 站点号 / 真实用户个号进公开仓库**；本篇不写下一篇手册正文。

## 2. 总图 / 故事：同一套前台，三条投诉线

### 2.1 一句话：三线都在「旅馆前台」，但成败标准完全不同

继续旅馆比喻（第 31–40 课 + 手册 01/02）：

| 旅馆 | 空口 | 本篇投诉常卡在哪 |
|------|------|------------------|
| 前台 | **TSCC** | 三线默认都在前台办，不进客房 |
| 前台发「暂停房卡权限」 | **Stun**（STUNI） | 人还在酒店里走动（登记/定位），却不能点餐——用户以为「没禁上」 |
| 前台发「恢复房卡权限」 | **Revive**（仍从 STUNI） | 业务应恢复；若未恢复才查空口 ACK |
| 前台发「永久销户」 | **Kill**（KILLI） | 不可空口 Revive；必须鉴权；终 ACK 丢了≠一定没生效 |
| 前台传纸条 | **短信 / UDT**（SDMI） | 个呼有回执镜像；组呼只保证「前台已广播」，不保证每人读到 |
| 前台发「今日临时工作牌清单」 | **DGNA**（DGNAI） | Address 模式 = **整表换牌**；漏写旧牌 → 「牌丢了」投诉 |

口诀：**先分线 → 再对成败标准 → 再开口回用户。**  
把「Stun 后地图还有点」写成故障，或把「组短信已送达」写成「对方已读」，是本篇最常见的两大口误。

### 2.3 对照图：三条「像故障其实是预期」

```text
  A. Stun 后地图还有点（常被误判）
     网管 Stun 成功 → 用户业务已停
     但猎站/登记/鉴权/定位仍可用
     ※ 「还有点」= 设计；「还能个呼/组呼/短信」才是失败

  B. 组短信「已送达」对方说没收到（常被误判）
     网络回 Message_Accepted（学习口径：网络已接受/已发给组）
     ※ 不是「某台手台已读」；先问个呼还是组呼

  C. DGNA 后旧动态组失踪（常被误判为「空口丢了」）
     Address 模式成功 → 整表替换 ADDRESS1…15
     ※ 新清单没带旧组 = 人为删除；要追加必须旧组一起再发
```

对照口诀：

| 你想确认的事 | 成功长什么样 | 失败 / 假故障长什么样 |
|--------------|--------------|------------------------|
| **Stun 办成了吗？** | 用户业务已停；登记/定位仍可 | 仍能个呼/组呼/短信 → 查空口 ACK / 是否未支持 |
| **Revive 办成了吗？** | 用户业务恢复 | 仍停业务 → 查是否真 Revive、空口是否成功 |
| **Kill 办成了吗？** | 全部 DMR 功能永久失去；空口不能 Revive | 鉴权失败则状态不变；无终 ACK 时可能已生效 |
| **个呼短信到了吗？** | 被叫 ACK + 镜像给主叫 | 无镜像 / NACK → 按信令排 |
| **组短信「到了」吗？** | 网络 Message_Accepted | **不等于**组员已读；覆盖/正忙于业务信道等 |
| **DGNA 加组办成了吗？** | 清单与预期一致（含旧组） | 漏带旧组 → 「组丢了」投诉 |

## 3. 三线分诊 + 「投诉三联单」

### 3.1 三线工作流（每次工单照念）

把下面三块贴在网管 / 投诉坐席屏边上（第 40 课 Week‑2 加厚）：

```text
① Stun 线（远程禁用 / 恢复 / 永久禁用）
   → 先确认操作意图：Stun？Revive？Kill？（网络管理口径）
   → 网关名片：STUNI=`FFFECC`（Stun/Revive）；KILLI=`FFFECF`（Kill）
   → 成败标准：**用户业务是否已停 / 已恢复**（个呼、组呼、短信、数据）
   → 「地图上还有没有点」「还在不在登记」**不是** Stun 失败证据——它们常被保留
   → Kill：永久；空口不能 Revive；必须鉴权；终 ACK 丢失时先核是否已生效
   → 不支持：常见空口口径 C_NACKU + MSNot_Supported（学习记 `0x00`）——与信号无关

② 短信线（短数据 / UDT）
   → **第一句：个呼还是组呼？**
   → 网关名片：SDMI=`FFFEC5`（TSCC 以它的名义「要货」）
   → 个呼：被叫应 ACK；主叫侧常见为镜像 Reason（学习口径：对方收妥才算「真到了」）
   → 组呼：网络 Message_Accepted（学习记 `0x60`）=「网络已发给这个组」
        **≠「某一台已读」**；组成员不回确认
   → UDT 长度教学点：头 + 1…4 附块 → 约 **80 / 176 / 272 / 368 bit**（变长二进制上限记法见第39课；本篇不手拼）
   → 过长 / 编码不符：先查长度与格式，再查射频

③ DGNA 线（动态组）
   → 网关名片：DGNAI=`FFFED6`
   → Address 模式：最多 15 个 24-bit 组号；**成功则整表替换**原 ADDRESS1…15
   → 漏带旧组 → 典型投诉「组丢了」——先查下发清单，别先骂空口
   → Alias 模式：再加 1 个带别名的组位（15+1=16）；预期与 Address 不同
   → 清空 / 删除：空位 ADRNULL 等写法回第39课 / 笔记；本篇话术强调「写清意图再下发」
```

**结束条件**：三线之一已选定 + 成败标准已对用户说清 + 空口/网管证据（脱敏）写入话术卡，才能谈「换机 / 重发 / 升级射频」。只有中文「禁了没反应 / 已送达没收到 / 组没了」= 线索不足。

### 3.2 决策树（口述版）

```text
工单：Stun异常 / 短信纠纷 / DGNA组丢了 / 「禁了还有点」
        │
        ▼
  主题分流：Stun？短信？DGNA？（可多线，但每次先钉一条主线）
        │
   Stun ──► 意图=Stun/Revive/Kill？
        │     业务已停/恢复？──是──► 用「预期说明」话术结案（地图有点=正常）
        │                    ──否──► 查空口 AHOY/ACK；MSNot_Supported？鉴权失败？
        │
   短信 ──► 个呼还是组呼？
        │     个呼：有无被叫ACK/镜像？──无──► 信令排障（可达/拒绝/超时）
        │     组呼：Message_Accepted？──是──► 「已送达≠已读」话术；查对方是否在控/覆盖
        │
   DGNA ──► Address 还是 Alias？
              Address：下发清单是否含全部应保留旧组？──否──► 「整表替换」说明+重发完整表
              Alias：是否误用 Address 预期检查？──是──► 换预期再查
```

### 3.3 投诉三联单（话术版 · 强制三栏）

手册 01/02 三联单服务登记与 Grant；本篇换一副「管理/短数据」三栏：

| 栏 | 必填 | 不及格写法 |
|----|------|------------|
| **A. 主题与意图** | Stun/Revive/Kill 或 个呼短信/组呼短信 或 DGNA Address/Alias；时间戳 | 「用户不满意」「短信有问题」 |
| **B. 空口 / 网管证据** | 网关 ID（STUNI/KILLI/SDMI/DGNAI）、ACK/Reason 学习名或码值、是否 Message_Accepted | 「网管绿勾」四个字无票样 |
| **C. 成败标准与回复** | 已对照效果表/个组呼语义；已用标准话术回复（可粘贴编号） | 「让用户再试一次」无标准 |

### 3.4 「中文提示 → 先分线」对照心态

| 坐席听见的中文 | 先做什么 | 不要先做什么 |
|----------------|----------|--------------|
| 「禁了还能看见位置」 | Stun 线：讲预期；核业务是否已停 | 立刻说「没禁上」 |
| 「恢复了还是不能打」 | Stun 线：核是否真 Revive、空口成败 | 先拧天线 |
| 「永久禁用一直转圈」 | Kill：鉴权/钥匙/终 ACK 丢失口径 | 连点十次 |
| 「已送达对方没收到」 | 短信线：先问个呼/组呼 | 先骂用户或先查功放 |
| 「组突然没了」 | DGNA：查最近一次 Address 清单是否漏旧组 | 先报「空口丢组」 |
| 「动态组名不对」 | 先分 Address vs Alias 预期 | 用 Address 清单话术硬套 |
